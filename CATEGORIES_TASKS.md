# Свои категории — инструкция для каждого участника

Неделя 30.10.2026. Цель: пользователь сам управляет категориями расходов и может вручную исправить, куда ML положил товар.

Что должен уметь пользователь:

1. **Добавить** свою категорию (например, «Косметика») с иконкой и описанием.
2. **Изменить** название, иконку и описание любой категории, в том числе стандартной.
3. **Удалить** любую категорию. Её товары — перенести в другую категорию или оставить без категории.
4. **Поменять порядок** категорий.
5. **Переложить товар** в другую категорию: перетащить мышью или выбрать из списка. Например, крем Nivea, который ML отнёс в «Дом и быт», — в «Косметику».
6. **Запомнить исправление**: в следующий раз такой же товар сразу попадёт в выбранную категорию.

Сначала все читают [раздел 0](#0-общие-договорённости-читают-все) — это общий контракт. Затем — раздел своей роли. Если в ходе работы контракт нужно поменять — сначала правка в этом файле и сообщение в чат команды, потом код.

## 0. Общие договорённости (читают все)

### 0.1. Что сейчас

- Категория — **строка** в трёх местах: `receipt_items.category`, `receipts.category`, `budgets.category`. Переименовать категорию нельзя: пришлось бы переписывать строки во всех чеках.
- Список из 8 категорий с иконками **зашит во фронт** (`CATEGORIES` в `app.js`, строка 4). Сервер его не знает и принимает любую строку.
- **ML категории не определяет**: в ответе Qwen всегда `"category": null`. Категорию угадывает фронт по ключевым словам (`keys` и `guessCategory` в `app.js`, строки 6–14 и 130).
- Сервер в аналитике пишет «Прочее», фронт — «Другое».

### 0.2. Как будет

| Понятие | Что это |
|---|---|
| **Категория** | Запись в таблице `categories`, у каждого пользователя свой набор. Поля: `id`, `name`, `description`, `icon`, `position` |
| **Стандартные категории** | 8 категорий, которые создаются каждому пользователю при регистрации (и старым — миграцией). После создания — обычные категории: их можно переименовать и удалить |
| **Без категории** | Позиция, у которой `category_id = null`. Это **не запись в таблице**: её нельзя переименовать или удалить. Интерфейс показывает её как «Без категории» |
| **Ссылка на категорию** | Позиция, чек и лимит бюджета хранят `category_id`, а не название. Переименование категории сразу видно везде |
| **Правило** | «Товар с таким названием → такая категория». Создаётся, когда пользователь переложил товар с галочкой «Запомнить». При распознавании правило важнее ML |
| **Источник категории** | Откуда у позиции категория после распознавания: `rule` — правило пользователя, `ai` — Qwen, `keywords` — ключевые слова, `null` — не определена |

### 0.4. Ограничения (одинаковые на фронте и на сервере)

| Поле | Правило | Ошибка сервера |
|---|---|---|
| `name` | Обрезать пробелы по краям; 1–50 символов | `422` «Название категории: от 1 до 50 символов» |
| `name` | Уникально у пользователя **без учёта регистра** («косметика» = «Косметика») | `409` «Категория «Косметика» уже есть» |
| `name` | Нельзя «Без категории» (без учёта регистра) — занято интерфейсом | `422` «Это название зарезервировано» |
| `description` | До 300 символов; пустая строка → `null` | `422` |
| `icon` | До 8 символов (один эмодзи может занимать несколько); пусто → `◌` | `422` |
| Категорий у пользователя | Не больше 50 | `422` «Можно создать не больше 50 категорий» |
| Чужой или несуществующий `category_id` | В любом запросе | `422` «Категория не найдена» (в пути URL — `404`) |

### 0.5. Категория чека

У чека остаётся своя категория (`receipts.category_id`): по ней считаются чеки без позиций, и она показывается плашкой в карточке. **Её всегда вычисляет сервер**, клиент её не присылает:

- есть позиции → категория позиции с наибольшей суммой (`total_price`); при равенстве — та, что раньше в списке позиций; позиции «Без категории» участвуют как `null`;
- позиций нет → то, что прислал клиент в `category_id` (единственный случай, когда поле чека учитывается), иначе `null`.

Пересчитывается при сохранении, редактировании чека и переносе позиций.

### 0.6. Нормализация названия товара для правил

Одна функция `normalize_item_name` в `app/categories.py`. Используют бэкенд (правила) и ML (если нужно сравнивать названия). Не копировать — импортировать.

```python
def normalize_item_name(name: str) -> str:
    """'Крем NIVEA 50мл' → 'крем nivea'. Пустая строка — правило не создаётся."""
    s = str(name or "").lower().replace("ё", "е")
    # числа с единицами; \b — чтобы «2 груши» не превратилось в «уши»
    s = re.sub(r"\d+(?:[.,]\d+)?\s*(?:(?:кг|гр|г|мл|л|шт|уп)\b|%)?", " ", s)
    s = re.sub(r"[^\w\s]", " ", s)                                     # знаки препинания
    s = re.sub(r"\s+", " ", s).strip()
    return s[:200]
```

Правило срабатывает при **точном совпадении** нормализованных названий.

Проверочные примеры (вынести в тест бэкенда):

| Вход | Результат |
|---|---|
| `Крем NIVEA 50мл` | `крем nivea` |
| `Крем Nivea 100 мл` | `крем nivea` |
| `2 груши` | `груши` |
| `Молоко 2,5% 1л` | `молоко` |
| `Шоколад Alpen Gold 85г` | `шоколад alpen gold` |
| `Ёлка` | `елка` |

### 0.7. API

🔒 — нужен токен. Ошибки — как в остальном API: `{"detail": "текст"}` на русском.

**Объект категории** (`CategoryOut`):
```json
{"id": 12, "name": "Косметика", "description": "Крем, шампунь, тушь, помада", "icon": "💄", "position": 8}
```

| Метод и путь | | Тело | Ответ |
|---|---|---|---|
| `GET /api/categories` | 🔒 | — | `[CategoryOut]`, по `position` |
| `GET /api/categories/defaults` | | — | `[{"name", "description", "icon"}]` — стандартные, для гостя |
| `POST /api/categories` | 🔒 | `{"name", "description"?, "icon"?}` | `201`, `CategoryOut`; `position` = последняя + 1 |
| `PATCH /api/categories/{id}` | 🔒 | любые из `name`, `description`, `icon` | `CategoryOut` |
| `DELETE /api/categories/{id}?move_to={id}` | 🔒 | — | `{"success": true, "moved_items": 14, "deleted_budget": true}` |
| `PUT /api/categories/order` | 🔒 | `{"ids": [3, 1, 12, …]}` — **все** id пользователя, каждый один раз | `[CategoryOut]` в новом порядке |
| `POST /api/items/move` | 🔒 | `{"item_ids": [101, 102], "category_id": 12, "remember": true}` | `{"moved": 2, "rules_created": 1}` |
| `GET /api/category-rules` | 🔒 | — | `[{"id", "pattern", "category_id", "category", "created_at"}]` |
| `DELETE /api/category-rules/{id}` | 🔒 | — | `{"success": true}` |

Подробности:

- **`DELETE` с `move_to`**: позиции, чеки и правила этой категории переходят в `move_to`. Без `move_to`: позиции и чеки → `null`, правила удаляются. **Лимит бюджета удаляемой категории удаляется в любом случае** (суммировать лимиты двух категорий молча — плохая идея). `move_to` = удаляемая категория или чужая → `422`.
- **`POST /api/items/move`**: `category_id: null` — «Без категории». Все `item_ids` должны принадлежать пользователю, иначе `404` и **ничего не меняется**. `remember: true` — для каждой позиции создать или обновить правило по `normalize_item_name(name)`; пустое нормализованное название — правило не создаётся; `category_id: null` — правило не создаётся. После переноса сервер пересчитывает категорию затронутых чеков (п. 0.5).

**Изменения в существующих ответах:**

Позиция чека (`ItemOut`) — в `/api/receipts…` и в ответе сохранения:
```json
{"id": 101, "name": "Крем Nivea", "quantity": 1, "price_per_unit": 1890, "total_price": 1890,
 "category_id": 12, "category": "Косметика"}
```
`id` — новое поле. **После `PUT /api/receipts/{id}` позиции пересоздаются и получают новые `id`** — фронт после редактирования перезагружает чеки.

Позиция в ответе `/api/analyze` — плюс `category_source`:
```json
{"name": "Крем Nivea", "total_price": 1890, "category_id": 12, "category": "Косметика", "category_source": "rule"}
```
У гостя `category_id` всегда `null`, а `category` — название стандартной категории.

Чек (`ReceiptOut`): поля `category_id` и `category` (название), как у позиции.

**Сохранение и редактирование чека** (`POST /api/receipts/save`, `PUT /api/receipts/{id}`), позиция:
- `category_id` — если есть, используется он;
- иначе `category` (название) — сервер ищет категорию пользователя с таким названием без учёта регистра; **не нашёл — `null`, новую не создаёт**;
- поле `category` у самого чека сервер игнорирует (п. 0.5).

**Бюджеты:**
- `GET /api/budgets` → `[{"category_id": 12, "category": "Косметика", "limit": 15000.0}]`; общий лимит — `category_id: null`.
- `PUT /api/budgets` → `{"budgets": [{"category_id": 12, "limit": 15000}, {"category_id": null, "limit": 150000}]}`. Старый формат с `category` (название) больше не принимается.
- `GET /api/budgets/status` — у каждого элемента добавляется `category_id`.

**Аналитика** `GET /api/analytics`: `by_category` остаётся словарём «название → сумма»; позиции без категории — под ключом `"Без категории"`. «Прочее» больше нигде не используется.

**Фильтр** `GET /api/receipts?category=…` заменяется на `?category_id=…` (`0` — «Без категории»).

### Шаг 2. Модели — [app/models.py](app/models.py)

```python
class Category(Base):
    __tablename__ = "categories"
    id = Column(Integer, primary_key=True, index=True)
    user_id = Column(Integer, ForeignKey("users.id", ondelete="CASCADE"), nullable=False, index=True)

    position = Column(Integer, nullable=False, default=0)

class CategoryRule(Base):
    __tablename__ = "category_rules"
    id = Column(Integer, primary_key=True, index=True)
    user_id = Column(Integer, ForeignKey("users.id", ondelete="CASCADE"), nullable=False, index=True)
    pattern = Column(String(200), nullable=False)          # normalize_item_name(...)
    category_id = Column(Integer, ForeignKey("categories.id", ondelete="CASCADE"), nullable=False)
    created_at = Column(DateTime, default=utcnow)
    # уникальность (user_id, pattern)
```

В `ReceiptItem`, `Receipt` и `Budget`:
- **убрать** строковую колонку `category`;
- добавить `category_id = Column(Integer, ForeignKey("categories.id", ondelete="SET NULL"), nullable=True, index=True)` (у `Budget` — `ondelete="CASCADE"`: лимит удалённой категории удаляется);

### Шаг 3. Миграция `0005_categories`

```powershell
alembic revision --autogenerate -m "свои категории" --rev-id 0005_categories
```

Файл после autogenerate **переписать вручную** — данные нужно перенести. Порядок в `upgrade()`:

1. Создать `categories` и `category_rules` (с проверкой, что таблиц ещё нет). Уникальный индекс `(user_id, pattern)` у правил.
2. Добавить `category_id` в `receipt_items`, `receipts`, `budgets` (через `batch_alter_table` для SQLite).
3. Для **каждого пользователя**:
   - создать 8 стандартных категорий (`DEFAULT_CATEGORIES`, копией в миграции — миграция не должна зависеть от будущих правок `app/categories.py`);
   - собрать все строки категорий из его позиций, чеков и бюджетов; `"Прочее"` считать `"Другое"`; пустые и `NULL` пропустить;
   - строки, которых нет среди стандартных (без учёта регистра, с обрезкой пробелов), — создать как категории пользователя с иконкой `◌`, `position` после стандартных;
   - проставить `category_id` позициям, чекам и бюджетам по названию.
4. Удалить строковые колонки `category` у трёх таблиц.

`downgrade()`: вернуть строковые колонки, заполнить их названиями по `category_id`, удалить `category_id`, удалить таблицы.

Проверить на **копии рабочей базы**: у каждого пользователя 8+ категорий; ни одна позиция с категорией не потеряла её; сумма по категориям в аналитике до и после миграции одинаковая (кроме «Прочее» → «Другое»).

### Шаг 1. Функция раскладки — `ml/app/categorize.py`

```python
def categorize_items(items: List[dict], categories: List[dict]) -> None:
    """Проставляет каждой позиции category_id, category и category_source ('ai' | 'keywords' | None).
    categories: [{"id": int | None, "name": str, "description": str | None}] — категории пользователя
    или стандартные (у гостя id = None). Меняет items на месте."""
```

Порядок:
1. **Qwen** (если `USE_AI_PARSER` не `0` и Ollama доступна) — шаг 2. Ответ для позиции принят → `category_source = "ai"`.
2. **Ключевые слова** для позиций, которые Qwen не разложил или Qwen недоступен — шаг 4. Нашлось → `"keywords"`.
3. Иначе — `category_id = None`, `category = None`, `category_source = None`.

**Возвращать только категории из переданного списка.** Новых категорий ML не придумывает. Ничего не подошло — `None`, а не «Другое»: пусть пользователь видит, что товар не разложен.

### Шаг 2. Запрос к Qwen

Отдельный короткий запрос (не в основном промпте разбора чека — он и так длинный):

- категории — **пронумерованным списком с 1** (не `id` из базы: так одинаково работает и у гостя), с описанием:
  ```
  1. Продукты — Еда и напитки для дома: молочные продукты, хлеб, мясо…
  8. Косметика — Крем, шампунь, тушь, помада
  ```
- товары — пронумерованным списком с 0;
- ответ — только JSON: `{"items": [{"index": 0, "category": 8}, {"index": 1, "category": null}]}`;
- номер вне списка, повтор `index`, не-JSON → для этих позиций ответа нет (уйдут в ключевые слова), исключение не бросать;
- `temperature: 0`, таймаут **30 с** (запрос идёт под общей блокировкой OCR — не держите её дольше);
- в промпте: «Описание категории важнее её названия. Если ни одна категория не подходит — null».

### Шаг 3. Подключение — `app/ocr.py`

### Шаг 4. Ключевые слова

1. **Из описаний категорий пользователя** — главный источник: так своя категория «Косметика» с описанием «крем, шампунь, тушь» начинает работать сразу, без Qwen. Слова описания: разбить по запятым, точкам с запятой и пробелам; в нижний регистр, `ё` → `е`; слова короче 3 букв выбросить; ключ — **первые 5 букв** слова (или всё слово, если короче).
