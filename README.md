# CheckAI — Интеллектуальный анализ кассовых чеков

Сервис на базе искусственного интеллекта для автоматического извлечения товаров, цен, количества, реквизитов организации и итоговой суммы из фотографий кассовых чеков. Распознанные чеки сохраняются в историю, раскладываются по категориям, учитываются в бюджетах и аналитике.

## Описание проекта

Обработка бумажных и электронных кассовых чеков вручную требует значительных временных затрат и подвержена человеческим ошибкам. **CheckAI** автоматизирует этот процесс:

1. Выполняет оптическое распознавание текста (OCR) с использованием нейросети PaddleOCR.
2. Передаёт распознанный текст языковой модели Qwen 2.5, которая извлекает товары, цены и реквизиты. Если модель недоступна, работает встроенный парсер на регулярных выражениях.
3. Фильтрует служебную информацию (адреса, реквизиты терминала, НДС, ФН/ФД/ФП) и раскладывает товары по категориям пользователя.
4. Предоставляет результат через веб-интерфейс (в том числе как приложение на телефоне) с сохранением в базу данных.

## Ключевые возможности

- **Локальное распознавание**: OCR и разбор чека выполняются на сервере, без отправки фото во внешние облачные API.
- **ИИ-парсинг**: Qwen 2.5 анализирует текст чека, исправляя ошибки OCR и структурируя данные.
- **Свои категории**: пользователь управляет списком категорий, переносит товары между ними, сервис запоминает правила «товар → категория».
- **Мультивалютность и курсы Нацбанка РК**: `KZT`, `RUB`, `USD`, `EUR`, `KGS`, `UZS`, `CNY`, `TRY` с пересчётом по курсу на дату покупки в основную валюту пользователя.
- **Бюджеты**: общий лимит на месяц и лимиты по категориям.
- **ИИ-рекомендации**: анализ расходов и советы (Gemini, Ollama или шаблонные советы без отправки данных).
- **Ручной ввод и защита от дубликатов**: чек можно ввести без фото; повторное сохранение того же чека распознаётся.
- **Три языка интерфейса**: русский, казахский, английский.
- **Аккаунты**: регистрация и вход по JWT, несколько аккаунтов на устройстве, профиль, фото профиля, восстановление пароля по коду.
- **Мобильная версия (PWA)**: устанавливается на главный экран телефона, съёмка чека камерой.
- **Экспорт**: чек в `.json`, история в `.csv`.
- **Docker**: проект запускается одной командой.

```

         │
         ▼

         │
         ▼
[ 4. FastAPI + Web UI ]
  • REST API, история, аналитика, бюджеты, рекомендации
  • SQLite или PostgreSQL
```

## Установка и запуск

Полная версия проекта (сайт, бэкенд, ML) — в ветке `main`. Перед запуском обновите её:

```powershell
git checkout main
git pull
```

Два способа запуска: **Docker** (ничего не нужно ставить, кроме Docker Desktop) и **без Docker** (быстрее для разработки).

### Кому какой режим

| Роль | Команда | Что поднимается | RAM |
|---|---|---|---|
| Бэкенд, фронтенд | `uvicorn server:app --reload` или `docker compose up -d` | Только сайт и API. Чеки распознаются запасным парсером `ml/parser.py`, Ollama не нужна | ~0,5 ГБ |
| ML | `docker compose --profile full up -d` или без Docker с установленной Ollama | Сайт + Ollama (Qwen 2.5:3b) | ~4–5 ГБ |
| Ollama уже стоит на компьютере | `docker compose up -d --build` + `DOCKER_OLLAMA_HOST` в `.env` (см. [вариант А2](#вариант-а2-docker--ollama-на-компьютере)) | Сайт в Docker, Qwen — из вашей Ollama. Модель не скачивается второй раз | ~4–5 ГБ |
| QA, демонстрация | `docker compose --profile full up -d --build` | Всё, как у пользователя | ~4–5 ГБ |

Без Ollama сайт, аккаунты, история и валюты работают, а распознавание чека переключается на запасной парсер (точность ниже).

### Подготовка (один раз)

Создайте файл `.env` с ключом для подписи токенов:

```powershell
copy .env.example .env
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Вставьте полученную строку в `.env` после `SECRET_KEY=`. Без `SECRET_KEY` сервер не запустится.

### Способ А. Docker

Нужен запущенный [Docker Desktop](https://www.docker.com/products/docker-desktop/). Ollama отдельно ставить не нужно.

```powershell
docker compose --profile full up -d --build
# Первый раз: скачать языковую модель (~2 ГБ)
docker compose exec ollama ollama pull qwen2.5:3b
```

Откройте `http://localhost:8000`. Остановить — `docker compose --profile full down`.

- Без `--profile full` Ollama не запускается — поднимается только сайт.
- Папки `app/`, `ml/`, `frontend/`, `migrations/` и `server.py` подключены к контейнеру напрямую: правки фронтенда видны после `F5`, правки Python — после `docker compose restart web` (`--reload` в контейнере не включён). `--build` нужен, когда меняются `requirements.txt` или `Dockerfile`; после `git pull` проще всегда запускать с `--build` — без изменений сборка занимает секунды.
- Миграции базы применяются сами при старте сервера.
- Модель распознавания загружается сразу при старте контейнера, а не при первом чеке (`OCR_WARMUP=1`). Файлы моделей PaddleOCR хранятся в volume `paddlex_models` и скачиваются только при самом первом запуске.

#### Вариант А2. Docker + Ollama на компьютере

Если Ollama уже установлена (как в способе Б) и модель скачана, второй контейнер с Ollama не нужен. Добавьте в `.env`:

```ini
DOCKER_OLLAMA_HOST=http://host.docker.internal:11434
```

и запускайте без профиля:

```powershell
docker compose up -d --build
```

Остановить — `docker compose down`. Ollama на компьютере должна быть запущена (значок в трее).

### Способ Б. Без Docker

Нужен **Python 3.11 или новее** (закреплённый `numpy 2.3` на 3.10 не ставится).

**Один раз:** установите [Ollama](https://ollama.com/download/windows) (в PowerShell — `irm https://ollama.com/install.ps1 | iex`), откройте новый терминал и скачайте модель; затем подготовьте окружение:

```powershell
ollama pull qwen2.5:3b

python -m venv .venv
.venv\Scripts\activate          # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
```

**Каждый раз:**

```powershell
.venv\Scripts\activate
uvicorn server:app --host 127.0.0.1 --port 8000 --reload
```

Откройте `http://localhost:8000`, Swagger (все эндпоинты, можно вызывать прямо из браузера) — `http://localhost:8000/docs`. Остановить — `Ctrl+C`. Ollama на Windows работает в фоне (значок в трее); если её нет — запустите из меню «Пуск».

- После `git pull` выполните `pip install -r requirements.txt`, если менялись зависимости.
- Старт занимает несколько секунд: сервер импортирует PaddlePaddle. Первое распознавание долгое: PaddleOCR загружает модель, а при самом первом запуске ещё и скачивает её в `~/.paddlex`.
- Чтобы не ждать попытки подключиться к Ollama, когда её нет, поставьте в `.env` `USE_AI_PARSER=0`.

### Проверка, что всё работает

1. `http://localhost:8000/api/health` — должно быть `"status": "healthy"` и `"ollama": "available"`. Поле `"ocr"`: `"standby"` — модель ещё не загружалась (без Docker она загружается при первом чеке), `"loading"` — загружается, `"ready"` — готова. В Docker через несколько секунд после старта должно стать `"ready"`.
2. Загрузите фото чека. Без Docker первый чек обрабатывается дольше — загружаются модели.
3. В логе сервера (`docker compose logs -f web`, без Docker — окно терминала с uvicorn) не должно быть строки «Qwen не разобрал чек… Используется встроенный парсер». Если она есть — Ollama не запущена или не скачана модель. После каждого чека в логе есть строка `analyze: ocr=…s llm=…s categorize=…s` — сколько секунд занял каждый этап.

### Тесты

Все тесты запускаются из корня проекта (~3 минуты). Тесты бэкенда сами работают на временной базе и во временных папках: рабочая `data/checkai.db` не трогается, `DATABASE_URL` из `.env` игнорируется. Тестам ML Ollama не нужна.

```powershell
.venv\Scripts\activate
python -m pytest -q             # все тесты
python -m pytest tests -q       # только бэкенд
python -m pytest ml/tests -q    # только ML
```

Проверка переводов интерфейса — `node scripts/check_i18n.js`.

### Частые проблемы

| Проблема | Решение |
|---|---|
| Команда `ollama` не найдена | Откройте новое окно терминала |
| `Set SECRET_KEY in .env` при запуске Docker | Заполните `SECRET_KEY` в `.env` |
| Распознавание слабое, позиции не находятся | Qwen не используется — см. пункт 3 проверки |
| После `git pull` в Docker старое поведение | `docker compose restart web`; если менялись зависимости — запустите с `--build` |
| `"ollama": "unavailable"` в Docker с Ollama на компьютере | Проверьте `DOCKER_OLLAMA_HOST` в `.env` и что Ollama запущена: `curl http://localhost:11434/api/version` |
| `No module named 'ollama'` при запуске тестов | Тесты запущены не из `.venv` — выполните `.venv\Scripts\activate` |
| Порт 8000 занят | Укажите другой: `--port 8001` |

## Веб-интерфейс

Интерфейс — HTML + CSS + JS без сборки: разметка в [`frontend/templates/index.html`](frontend/templates/index.html), стили в [`frontend/static/css/app.css`](frontend/static/css/app.css), логика в [`frontend/static/js/app.js`](frontend/static/js/app.js) (сервер отдаёт их по адресу `/static/...`). Все данные он получает через REST API; к базе напрямую не обращается.

### Разделы

| Раздел | Что делает |
|---|---|
| **Добавить чек** | Загрузка фото или съёмка камерой телефона (или демо-чек), ручной ввод без фото, распознавание с показом этапов, правка распознанного чека, сохранение в историю, скачивание JSON |
| **История и расходы** | Список чеков за период, поиск по магазину и товару, сумма, средний чек, экспорт в CSV. Клик по чеку открывает подробности |
| **Категории** | Свои категории: добавить, изменить название, иконку и описание, удалить, поменять порядок. Расходы по категориям за период, товары категории, перенос товара в другую категорию (перетаскиванием или списком) с запоминанием правила |
| **Анализ расходов** | График по дням/месяцам, разбивка по категориям, ИИ-рекомендации |
| **Бюджеты** | Общий лимит на месяц и лимиты по категориям, предупреждения о перерасходе |
| **Профиль** | Данные аккаунта, фото, сводка и привычки, оформление, язык, аккаунты на устройстве, редактирование и удаление аккаунта (виден только после входа) |

### Аккаунты

- **Гостевой режим.** Распознавать чеки можно без входа. При нажатии «Сохранить в историю» открывается окно входа; после входа чек сохраняется автоматически.
- **Вход и регистрация** — кнопка «Войти / Регистрация» в шапке. Access-токен (живёт час) хранится в `localStorage` (`checkai_token`) и отправляется в заголовке `Authorization: Bearer <токен>`, refresh-токен (30 дней) — в `checkai_refresh`. Если access-токен истёк (ответ `401`), интерфейс один раз обновляет пару через `POST /api/auth/refresh` и повторяет запрос; если не получилось (refresh истёк или пароль сменили), переходит в гостевой режим.
- **Меню аккаунта** — клик по аватару в шапке: «Профиль и настройки», список других аккаунтов, «Добавить аккаунт», «Выйти».
- **Смена аккаунта.** Каждый аккаунт, в который входили на этом устройстве, запоминается (до 5 штук, `localStorage` → `checkai_accounts`). Переключение — в меню аккаунта или в профиле, без повторного ввода пароля. Если сохранённая сессия истекла, откроется вход с подставленным email. Крестик в профиле убирает аккаунт с устройства.
- **Выход** удаляет текущий аккаунт из списка сохранённых на устройстве.
- **Редактирование аккаунта** (Профиль): имя, email, новый пароль, основная валюта. Для смены email или пароля нужен текущий пароль.
- **Удаление аккаунта** (Профиль): требует пароль и подтверждение; удаляет аккаунт и все его чеки.
- **Смена пароля** завершает все остальные сессии этого аккаунта: старые токены перестают действовать, текущая вкладка получает новые.
- **Забыли пароль** — сброс по коду восстановления, который показывается один раз при регистрации (новый код можно получить в профиле).

### Подробности покупки

Клик (или `Enter`) по чеку в истории открывает карточку: магазин, дата и время покупки, итог, категория, дата сохранения, фото чека (если сервер вернул `image_path`), все позиции с количеством, ценой и категорией. Если сумма позиций расходится с итогом чека больше чем на 1 ₸, показывается предупреждение — это признак ошибки распознавания. Из карточки можно скачать чек в JSON или удалить его.

Кнопка «Редактировать» в карточке открывает ту же форму, что и после распознавания. Сохранение отправляет `PUT /api/receipts/{id}` (тело как у `POST /api/receipts/save`).

### Добавление чека

- Файл проверяется до отправки: JPG, PNG, WEBP, BMP или TIFF, не больше 10 МБ (как `MAX_UPLOAD_MB` на сервере). Для HEIC с iPhone показывается подсказка, как сохранить фото в JPG.
- JPG, PNG и WEBP браузер сжимает перед отправкой: короткая сторона (ширина чека) — до 1600 px, JPEG 85%. Длинную сторону отдельно не режем, чтобы длинный чек остался читаемым. Поэтому для этих форматов можно выбрать файл до 40 МБ — на сервер уйдёт уже сжатый.
- Распознавание идёт фоновой задачей: `POST /api/analyze/async` → опрос `GET /api/tasks/{id}`. Если на телефоне погас экран или браузер выгрузил вкладку, после возврата распознавание продолжается (id задачи хранится в `sessionStorage`).
- Во время распознавания видны этапы «Загрузка → Распознавание текста → Анализ» и прошедшее время, кнопки заблокированы. Прогресс загрузки — настоящий; переход к «Анализу» сервер не сообщает, он показывается примерно через 5 секунд после загрузки.
- Распознанный чек сразу открывается в форме: магазин, дата, время, валюта, позиции (название, количество, цена, сумма, категория), итог. Сумма строки пересчитывается при смене количества или цены; если сумма позиций не совпадает с итогом, можно одной кнопкой сделать её итогом.
- Если такой чек уже есть в истории (то же фото, фискальный номер или содержимое), перед сохранением показывается предупреждение с возможностью сохранить всё равно.

### Прочее

- **Экспорт CSV** — выгружает чеки, видимые в истории с учётом периода и поиска, по строке на позицию. Разделитель `;` и запятая в дробях — файл открывается в Excel без настройки.
- **Тема и акцентный цвет** — в профиле. По умолчанию берётся тема системы.
- **Язык** — переключатель в шапке: русский, казахский, английский. Выбор запоминается, у вошедшего — на сервере.
- **История** загружается с сервера порциями по 200 чеков и показывается по 20 с кнопкой «Показать ещё».

### Мобильная версия (PWA)

Это тот же сайт: телефон показывает интерфейс, распознавание (PaddleOCR, Qwen) по-прежнему делает сервер, поэтому сервер должен быть запущен и доступен с телефона.

- **На телефоне** (ширина до 700 px) у вошедшего пользователя внизу панель разделов: История, Анализ, ＋ Чек, Бюджеты, Категории. Пока открыта клавиатура, панель скрыта. Окна выезжают снизу. Кнопка «Назад» (жест на Android) закрывает открытое окно, затем возвращает к прошлому разделу.
- **Установка на главный экран**: Chrome/Edge — пункт «Установить приложение» в меню и в «Профиль → Оформление»; iPhone — Safari → «Поделиться» → «На экран „Домой“». Нужен HTTPS (или `localhost`).
- **Без сети** интерфейс открывается из кэша service worker'а, данные — нет (нужна связь с сервером).
- Файлы: `frontend/static/manifest.webmanifest` и `frontend/static/sw.js` (сервер отдаёт их из корня: `/manifest.webmanifest`, `/sw.js`), иконки — `frontend/static/icons/`.
- **Service worker на localhost выключен**, чтобы кэш не прятал правки при разработке. Включить для проверки: в консоли браузера `localStorage.checkai_sw = '1'` и перезагрузить страницу; выключить — удалить ключ. На рабочем сайте (HTTPS) он включён всегда. Поменяли `sw.js` — поднимите в нём `VERSION`; поменяли CSS/JS — поднимите `?v=` в `index.html`.

**Как открыть с телефона:**
1. Одна Wi-Fi сеть: `http://<IP компьютера>:8000` (IP — `ipconfig` → IPv4; может понадобиться разрешить порт 8000 в брандмауэре Windows). Работает всё, кроме установки приложения и service worker'а — для них нужен HTTPS.
2. HTTPS-туннель — для проверки установки и показа: VS Code → панель **Ports** → **Forward a Port** → `8000` → правый клик → **Port Visibility → Public**, адрес вида `https://…devtunnels.ms` открыть на телефоне. Или `cloudflared tunnel --url http://localhost:8000`. Пока идёт показ, компьютер, Docker и Ollama должны работать. Публичная ссылка доступна всем, у кого она есть, — после показа остановите туннель.

### Справочник валют

- **URL**: `GET /api/currencies` (без авторизации)
- **Ответ**: Список поддерживаемых валют, `name` — на языке запроса:
  ```json
  [
    {"code": "KZT", "symbol": "₸", "name": "Казахстанский тенге", "digits": 0},
    {"code": "USD", "symbol": "$", "name": "Доллар США", "digits": 2}
  ]
  ```

### Регистрация и вход

- **URL**: `POST /api/auth/register` — тело `{"email", "password", "full_name"?}`
- **URL**: `POST /api/auth/login` — тело `{"email", "password"}`
- **Ответ**: `{"access_token", "refresh_token", "token_type": "bearer", "user": {"id", "email", "full_name", "base_currency": "KZT", "created_at", ...}}`. При регистрации — ещё `recovery_code` (показывается один раз).
- **Ошибки**: `400` с `{"detail": "..."}`, `422` — ошибки валидации, `429` — больше 10 попыток в минуту с одного IP
- **URL**: `POST /api/auth/refresh` — тело `{"refresh_token"}`, ответ как у входа (новая пара токенов). `401`, если refresh-токен истёк, подделан или пароль с тех пор сменили.

Access-токен живёт 60 минут, refresh-токен — 30 дней. В оба токена записан отпечаток пароля: после смены пароля все выданные раньше токены перестают действовать.

### Аккаунт пользователя

- 🔒 `GET /api/auth/me` — текущий пользователь (содержит `base_currency`, по умолчанию `"KZT"`).
- 🔒 `PATCH /api/auth/me` — смена данных. Тело (все поля необязательны):
  ```json
  { "full_name": "Новое имя", "email": "new@example.com", "new_password": "...", "current_password": "...", "base_currency": "USD" }
  ```
  `current_password` обязателен при смене `email` или `new_password`. Для смены имени, `base_currency`, оформления, языка и согласия на ИИ-анализ пароль не требуется. Ответ — как у входа: новая пара токенов и пользователь. Ошибки — `400` с `detail` (неверный текущий пароль, email занят), `422` при неподдерживаемой валюте.
- 🔒 `DELETE /api/auth/me` — удаление аккаунта. Тело `{"password": "..."}`. Удаляет пользователя, все его чеки и их фото, ответ `{"success": true}`. Неверный пароль — `400`.

### Анализ чека

- **URL**: `POST /api/analyze`
- **Тип**: `multipart/form-data`
- **Параметр**: `file` — изображение чека (JPEG, PNG, WebP, BMP, TIFF), до `MAX_UPLOAD_MB` (10 МБ)
- **Ответ**: `{"success": true, "data": {...}}` — поля описаны в разделе [Формат ответа распознавания](#формат-ответа-распознавания).
- **Категории позиций**: токен необязателен. С ним раскладка идёт по категориям и правилам пользователя, у гостя — по стандартным категориям, и `category_id` всегда `null`.
- **Ограничение**: 15 запросов в минуту с одного IP
- **Фоновый вариант** (его использует интерфейс): `POST /api/analyze/async` с тем же `file` → `202 {"task_id": "...", "check_url": "/api/tasks/<id>"}`; затем `GET /api/tasks/{task_id}` → `status` (`pending` / `processing` / `completed` / `failed`), в `result` — те же `data`, в `error` — текст ошибки на языке запроса. Задачу, запущенную с токеном, читает только её владелец: без токена или с истёкшим — `401`, с чужим — `404`. Задачи гостя и ИИ-анализ расходов — без авторизации.

### Сохранение чека в БД

- 🔒 **URL**: `POST /api/receipts/save`
- **Тип**: `application/json`
- **Тело**: JSON с данными чека (`store`, `date`, `time`, `total`, `currency` (по умолчанию `"KZT"`), `image_path`, `items[]`). Неизвестная валюта → `422`. Без `image_path` чек считается введённым вручную (`source: "manual"`).
- **Категория позиции**: `category_id` (чужой или несуществующий → `422` «Категория не найдена»); без него — `category` (название, без учёта регистра; категории с таким названием нет — `null`, новая не создаётся).
- **Категория чека** вычисляется сервером: категория самой дорогой позиции, при равенстве — первой из них. `category_id` чека учитывается, только если позиций нет.
- **Дубликат**: если такой чек уже сохранён (то же фото, фискальный номер или содержимое) — `409` с `duplicate_of` и `duplicate`. С `allow_duplicate: true` чек сохраняется всё равно.
- **Ответ**: Сохранённый чек с полями `category_id`, `category`, `currency`, `rate_to_kzt` (официальный курс НБ РК на дату чека), `base_currency`, `rate_to_base` (множитель к основной валюте пользователя; `null`, если курс недоступен). У позиций есть `id`, `category_id` и `category`.

### Получение истории чеков

- 🔒 **URL**: `GET /api/receipts?skip=0&limit=100` (`limit` до 500)
- **Фильтры** (необязательны): `from` и `to` — даты покупки `ГГГГ-ММ-ДД` включительно; `category_id` — чеки, где есть позиция этой категории (у чека без позиций — его собственная), `0` — «Без категории»; `q` — поиск по магазину и названиям товаров без учёта регистра
- **Ответ**: Список чеков пользователя (новые по дате покупки первыми) вместе с позициями, `currency`, `base_currency`, `rate_to_base`

### Один чек и редактирование

- 🔒 `GET /api/receipts/{id}` — один чек с позициями (`404`, если его нет или он чужой)
- 🔒 `PUT /api/receipts/{id}` — заменить данные чека (принимает `currency`; без него валюта чека не меняется); курс берётся заново при смене даты или валюты, а также если раньше его получить не удалось. Позиции заменяются целиком и **получают новые `id`** — после редактирования перечитайте чеки. Если правка сделала чек копией другого — `409`, как при сохранении.

### Аналитика

- 🔒 **URL**: `GET /api/analytics`
- **Ответ**: Сводная статистика по чекам в основной валюте пользователя (`base_currency`), а также `unconverted: [{"currency": "USD", "receipts": 2}]` (чеки, для которых нет курса, не входят в общие суммы). `receipts_count` — все чеки, `converted_count` — вошедшие в суммы; `avg_receipt` считается по учтённым. `by_category` — словарь «название → сумма», позиции без категории — под ключом `"Без категории"`

### Категории

Категории у каждого пользователя свои: при регистрации создаются 8 стандартных (Продукты, Одежда, Дом и быт, Транспорт, Кафе, Здоровье, Развлечения, Другое), дальше их можно переименовывать, удалять и добавлять свои. «Без категории» — это `category_id: null`, а не категория. По описанию категории ИИ раскладывает товары.

Объект категории: `{"id": 12, "name": "Косметика", "description": "Крем, шампунь, тушь, помада", "icon": "💄", "position": 8, "default_key": null}`. `default_key` — ключ нетронутой стандартной категории (по нему фронт показывает перевод названия), у своей или переименованной — `null`.

| Метод и путь | | Тело | Ответ |
|---|---|---|---|
| `GET /api/categories` | 🔒 | — | Категории по `position` |
| `GET /api/categories/defaults` | | — | `[{"name", "description", "icon", "default_key"}]` — стандартные, для гостя |
| `POST /api/categories` | 🔒 | `{"name", "description"?, "icon"?}` | `201`, категория в конце списка |
| `PATCH /api/categories/{id}` | 🔒 | любые из `name`, `description`, `icon` | Категория |
| `DELETE /api/categories/{id}?move_to={id}` | 🔒 | — | `{"success": true, "moved_items": 14, "deleted_budget": true}` |
| `PUT /api/categories/order` | 🔒 | `{"ids": [3, 1, 12, …]}` — все id пользователя, каждый один раз | Категории в новом порядке |
| `POST /api/items/move` | 🔒 | `{"item_ids": [101, 102], "category_id": 12, "remember": true}` | `{"moved": 2, "rules_created": 1}` |
| `GET /api/category-rules` | 🔒 | — | `[{"id", "pattern", "category_id", "category", "created_at"}]` |
| `DELETE /api/category-rules/{id}` | 🔒 | — | `{"success": true}` |

- **Ограничения**: `name` — 1–50 символов после обрезки пробелов, уникально без учёта регистра (`409` «Категория «Косметика» уже есть»), нельзя «Без категории» (`422`); `description` — до 300 символов, пустое → `null`; `icon` — до 8 символов, пустое → `◌`; не больше 50 категорий (`422`). Создание — не больше 30 в минуту с одного IP.
- **Удаление**: с `move_to` позиции, чеки и правила переходят в эту категорию; без него позиции и чеки остаются без категории, а правила удаляются. Лимит бюджета удаляемой категории удаляется в любом случае. `move_to` — та же или чужая категория → `422`. Чужая категория в пути → `404`.
- **Перенос позиций**: `category_id: null` — «Без категории». Хотя бы одна позиция чужая → `404`, не переносится ни одна. `remember: true` — запомнить правило «название товара → категория» (название нормализуется: «Крем NIVEA 50мл» и «Крем Nivea 100 мл» → `крем nivea`); при `category_id: null` правило не создаётся. `rules_created` — сколько правил создано или перенаправлено в другую категорию. Категории затронутых чеков пересчитываются.

### Удаление чека

- 🔒 **URL**: `DELETE /api/receipts/{id}`

### Бюджеты и лимиты расходов

- 🔒 **URL**: `GET /api/budgets`
  - **Ответ**: Список установленных лимитов текущего пользователя (общий лимит первым, затем в порядке категорий):
    ```json
    [
      {"category_id": null, "category": null, "limit": 150000.0},
      {"category_id": 12, "category": "Кафе", "limit": 15000.0}
    ]
    ```
    Если лимиты не заданы, возвращается `[]` со статусом `200` (а не `404`).
- 🔒 **URL**: `PUT /api/budgets`
  - **Тело**: `{"budgets": [{"category_id": 12, "limit": 15000.0}, {"category_id": null, "limit": 150000.0}]}`. `category_id: null` — общий лимит.
  - **Поведение**: Полная замена всех лимитов пользователя в одной транзакции. Ответ в том же формате, что у `GET /api/budgets`. Лимиты задаются в основной валюте пользователя.
  - **Валидация (`422`)**: `limit > 0` и `limit <= 1e12`; чужой или несуществующий `category_id` — «Категория не найдена»; дубликаты категорий (в том числе повторный `null`) запрещены; не более 50 лимитов на пользователя.
- 🔒 **URL**: `GET /api/budgets/status?month=YYYY-MM`
  - **Параметры**: `month` (необязательно, формат `ГГГГ-ММ`, по умолчанию — текущий месяц по UTC).
  - **Ответ**: Фактический расчёт расходов за месяц по каждому лимиту:
    ```json
    {
      "month": "2026-10",
      "total_budget": 150000.0,
      "total_spent": 45000.0,
      "budgets": [
        {
          "category_id": 12,
          "category": "Кафе",
          "limit": 15000.0,
          "spent": 16200.0,
          "remaining": -1200.0,
          "percent": 108.0,
          "percentage": 108.0,
          "is_over_budget": true
        }
      ]
    }
    ```

### ИИ-рекомендации

- 🔒 `GET /api/insights` — последний анализ на языке запроса: `{insights: {summary, items[]}, created_at, model, stale, retry_after}` или `{"insights": null}`. `stale: true` — с момента анализа данные изменились. `retry_after` — через сколько секунд можно запросить новый (`0` — уже можно).
- 🔒 `POST /api/insights` — новый анализ в фоне: `202 {task_id}`, результат — через `GET /api/tasks/{task_id}`. Если данные не изменились — `200` с прежним анализом. Чаще одного раза в `INSIGHTS_REFRESH_MINUTES` — `429` с `retry_after`. Без согласия пользователя (`preferences.ai_insights` в `PATCH /api/auth/me`) — `403`.
- Цифры для анализа считает сервер, текст пишет модель (`AI_PROVIDER`: Gemini, Ollama или `off` — только шаблонные советы). Ответ модели проверяется: выдуманные числа и текст не на том языке отбрасываются.

```json
  "merchant": "Magnum",
  "date": "2025-07-29",
  "time": "16:36",
  "currency": "KZT",
  "currency_source": "symbol",
  "total": 785.0,
  "items": [
    {
      "name": "Кофе американо",
      "quantity": 1,
      "price_per_unit": 100.0,
      "total_price": 100.0,
      "category_id": 5,
      "category": "Кафе",
      "category_source": "ai",
      "confidence": 0.93
    }
  ],
  "confidence": 0.88,
  "fiscal": {"fp": "...", "number": "...", "kkm": "...", "qr": "..."},
  "duplicate_of": null,
  "parser_used": "ai",

  "raw_lines": ["..."],

```

| Поле | Значение |
|---|---|
| `store` / `merchant` | Название как на чеке / каноническое имя сети (по нему группируются магазины) |
| `date`, `time` | `YYYY-MM-DD` и `HH:MM` или `null` |
| `currency_source` | `symbol` — символ или слово валюты на чеке, `country` — по реквизитам страны, `default` — подставлен `KZT` |
| `category_source` | `rule` — правило пользователя (важнее ИИ), `ai` — Qwen, `keywords` — словарь и ключевые слова, `null` — категория не определена |
| `confidence` | Уверенность распознавания 0..1 — у чека и у каждой позиции. По ней фронт подсвечивает сомнительные места |

| `duplicate_of` | id уже сохранённого чека с тем же фото или фискальным номером, иначе `null` |
| `warnings` | Коды предупреждений, например `sum_mismatch` — сумма позиций не сходится с итогом |
| `image_path` | Передаётся обратно в `POST /api/receipts/save` |

Нет текста на фото — `422`. Ошибка OCR — `500` с общим текстом, подробности только в логе сервера.

### Осторожно: что сервер делает с данными сам

**Очистка фото.** При старте и затем раз в `ORPHAN_CLEANUP_HOURS` часов сервер удаляет из `UPLOADS_DIR` все изображения старше суток, на которые не ссылается ни один чек **в текущей базе** (`cleanup_orphan_images` в [server.py](server.py)). Если подключить другую или пустую базу к той же папке — фото чеков из вашей основной базы будут удалены. Поэтому:

> Экспериментируете с другой базой — всегда задавайте вместе с `DATABASE_URL` и свой `UPLOADS_DIR`.

```powershell
$env:DATABASE_URL = "sqlite:///data/sandbox.db"
$env:UPLOADS_DIR  = "data/sandbox_receipts"
python -m uvicorn server:app --reload
```

Всё внутри `data/` игнорируется git, кроме `.gitkeep`.

**Миграции.** При импорте `server.py` вызывается `database.init_db()`, который доводит базу до последней миграции. Это происходит и при запуске тестов, и при запуске `uvicorn`. Старую базу без истории Alembic он сначала «усыновляет» (помечает ревизией `0001_baseline`).

### Устройство сервера

```
Браузер (frontend/, без сборки)
   │  fetch /api/*  + Authorization: Bearer <access>
   ▼
server.py — FastAPI
   ├─ middleware: лимит запросов, отсечение больших загрузок, nosniff
   ├─ обработчики ошибок: 422 без «Value error,», AppError/CategoryError → {detail, code}
   ├─ эндпоинты (def, выполняются в пуле потоков)
   │     ├─ app/auth.py      JWT, пароли, текущий пользователь
   │     ├─ app/schemas.py   Pydantic: проверка входа и формат ответа
   │     ├─ app/crud.py      все запросы к БД
   │     │     └─ app/models.py → app/database.py → SQLite / PostgreSQL
   │     └─ app/ocr.py → ml/ocr.py   распознавание (под общей блокировкой)
   │           ├─ preprocess → PaddleOCR → строки текста
   │           ├─ agent_parser.py   Qwen через Ollama (если доступна)
   │           ├─ parser.py         запасной парсер на regex
   │           └─ categorize.py, confidence.py, fiscal.py, merchant.py
   ├─ app/tasks.py — фоновые очереди: распознавание и ИИ-анализ
   ├─ /data/receipts/*, /avatars/*  — статика: только фото
   └─ /static/*                     — CSS и JS интерфейса
```

Главные решения:

- **Эндпоинты объявлены через `def`, а не `async def`.** FastAPI выполняет их в пуле потоков, поэтому долгий OCR не блокирует остальные запросы. Не делайте эндпоинты `async`, если внутри синхронная работа с БД или OCR.
- **Одна модель OCR на процесс.** `get_ocr()` создаёт её лениво (или при старте, если `OCR_WARMUP=1`). PaddleOCR не потокобезопасен, поэтому распознавание идёт под `_ocr_run_lock` — строго по одному.
- **Бизнес-логика запросов к БД — только в `crud.py`.** Эндпоинт проверяет права и вызывает функцию из `crud`.
- **Фронт получает данные только через API**, к базе не обращается.
- **Папка `ml/` — зона ML-разработчика.** Бэкенд вызывает из неё `ml.ocr` (через `app/ocr.py`), `ml.categorize`, `ml.advisor` и `ml.merchant`.

### Модель данных

```
users ──< receipts ──< receipt_items
  │          │              │
  │          └──────┬───────┘ category_id (SET NULL)
  ├──< categories <─┤
  │                 ├── budgets.category_id (CASCADE)
  │                 └── category_rules.category_id (CASCADE)
  ├──< budgets
  ├──< category_rules
  └──< insights (CASCADE)

exchange_rates (курсы валют к тенге на даты покупок)
```

| Таблица | Заметки |
|---|---|
| `users` | `base_currency` — основная валюта для аналитики и бюджетов (по умолчанию `KZT`). `preferences` — оформление, язык, согласие на ИИ-анализ. `recovery_code_hash` — bcrypt-хеш кода восстановления. Удаление пользователя каскадно удаляет его чеки, бюджеты, категории, правила и анализы |
| `categories` | Свой набор у каждого пользователя; при регистрации — 8 стандартных. `name` уникально у пользователя без учёта регистра (проверяет `crud`, индекса нет). `default_key` — ключ нетронутой стандартной категории для перевода. По `description` ML раскладывает товары |
| `category_rules` | «Товар → категория»: `pattern` — `normalize_item_name(название)`, уникальный индекс `(user_id, pattern)`. При распознавании правило важнее ML |
| `receipts` | `currency` — валюта чека (ISO 4217), `rate_to_kzt` — курс к тенге на дату чека. `category_id` вычисляет сервер. `source` — `photo` или `manual`. `image_hash` — SHA-256 файла фото, `fiscal_id` — `РНМ:номер:ФП`; индексы по ним не уникальные, чтобы «Всё равно сохранить» работало |
| `receipt_items` | Суммы в валюте чека. `category_source` — кто выбрал категорию. При редактировании чека позиции заменяются целиком и получают новые `id` |
| `budgets` | Лимиты в основной валюте пользователя. `category_id = NULL` — общий лимит на месяц. Лимит удаляется вместе с категорией |
| `exchange_rates` | Официальные курсы Нацбанка РК. Уникальный индекс `(date, currency)` |
| `insights` | ИИ-анализ расходов: `data` — `{summary, items}`, `language` — язык текста, хранятся последние. `snapshot_hash` — хеш сводки без точного дня: совпал — повторно не генерируем, не совпал — анализ `stale` |

Форматы, которые нельзя нарушать:

- **`receipts.date`** — строка `YYYY-MM-DD` или `NULL`, **`receipts.time`** — `HH:MM` или `NULL`. Строки в таком виде правильно сортируются и сравниваются прямо в SQL (фильтры `from`/`to`, месяц в бюджетах через `substr(date, 1, 7)`). Любую входящую дату прогоняйте через `app.dates.normalize_date_time` — схемы `ReceiptCreate`/`ReceiptUpdate` уже делают это.
- **`created_at`** — UTC без часового пояса (`models.utcnow()`). Фронт сам добавляет `Z` при показе.
- **`image_path`** — URL вида `/data/receipts/<32 hex>.<ext>`. Путь от клиента всегда проверяется `_resolve_image_path` — иначе можно сослаться на чужой или несуществующий файл. Старый формат `/data/receipts/<uuid>_<имя>.jpg` поддерживается только для уже сохранённых чеков.
- **Категории** — только ссылкой `category_id`; названия в чеках, позициях и бюджетах не хранятся, поэтому переименование сразу видно везде. В ответах название отдаёт свойство `category` модели (через `category_rel`), поэтому запросы, которые читают категории многих позиций, делайте с `joinedload(...category_rel)`. «Без категории» — `NULL`, а не запись; в аналитике — ключ `"Без категории"`. Категорию из запроса всегда проверяйте на владельца (`resolve_category_id` / `get_user_category`): чужая — `422` в теле, `404` в пути URL.
- **Категорию чека вычисляет сервер**: категория самой дорогой позиции, при равенстве — первой (`main_category_id`); у чека без позиций — присланный `category_id`. Пересчитывается при сохранении, редактировании и переносе позиций.
- **Валюты и деньги** — `Float`. Суммы и цены позиций хранятся в валюте чека. Все сводки сервер пересчитывает в `base_currency` пользователя через `rate_to_base`. **При чтении (`GET`) в сеть за курсами не ходим никогда** (`fetch=False`), запрос к Нацбанку — только при сохранении и редактировании чека. Чеки без курса не суммируются, а группируются в `unconverted`.

### Авторизация

Реализация — [app/auth.py](app/auth.py).

- Пароли — bcrypt. Длина пароля: от 8 символов и не больше 72 байт (bcrypt игнорирует всё дальше).
- **Access-токен** — JWT на 60 минут, **refresh-токен** — JWT на 30 дней. В оба пишется `type` (`access` / `refresh`) — токен одного типа нельзя использовать вместо другого.
- В токены пишется `pwd` — отпечаток хеша пароля. **После смены пароля все выданные токены перестают действовать** — так «выход со всех устройств» работает без таблицы сессий. `PATCH /api/auth/me` возвращает новую пару токенов, фронт её сохраняет.
- Сервер не хранит сессии: выход — это удаление токенов на фронте.
- **Сброс пароля — по коду восстановления, без почты.** Код вида `K7QF-2M9X-HD4P-WN3C` сервер отдаёт один раз, в базе — только его bcrypt-хеш. Неверный код и несуществующий email дают одинаковый `400`.
- Ошибки входа и смены данных — `400` с понятным текстом, не `401`: на `401` фронт считает, что сессия истекла, и выкидывает пользователя.

### Правила и соглашения

**Доступ к данным**

- Каждый запрос к чекам, категориям и бюджетам фильтруется по `user_id` текущего пользователя — внутри функций `crud`, а не после выборки.
- Чужой объект для пользователя «не существует»: отвечаем **`404`, а не `403`**, чтобы нельзя было перебором узнать, какие id заняты.

**Ошибки**

- Тексты ошибок — для пользователя: фронт показывает `detail` как есть. Технические подробности — только в лог (`logger.exception`).
- Ошибки, которые нужно перевести, бросайте как `AppError(статус, код)` с текстами в [app/i18n.py](app/i18n.py) — ответ будет `{"detail": текст на языке запроса, "code": код}`. В валидаторах схем — `raise ValueError("Понятный текст")`; приставка `Value error,` убирается обработчиком в `server.py`.
- Коды: `400` — неверные данные, которые нельзя проверить схемой (неверный пароль, занятый email); `401` — нет или истёк токен; `403` — нет согласия; `404` — нет объекта или он чужой; `409` — дубликат; `413` — файл больше лимита; `415` — не изображение; `422` — не прошла валидация; `429` — лимит запросов.

**Код**

- Запросы к БД — в `crud.py`, эндпоинты — в `server.py`, схемы — в `schemas.py`.
- Схемы ответа указывайте в `response_model` — так в ответ не попадут лишние поля (например, `hashed_password`).
- Новые настройки — в `app/config.py` через `os.getenv` с разумным значением по умолчанию, плюс строка в `.env.example` и в `docker-compose.yml`.
- Новые тексты интерфейса — в `scripts/i18n_source.py` (перевод на kk и en), затем `python scripts/i18n_source.py` и `node scripts/check_i18n.js`.
- Комментарии и docstring — на русском, объясняют «почему», а не пересказывают код.
- Зависимости закрепляйте точной версией в `requirements.txt`.

### Как добавить эндпоинт

Пример: заметка к чеку `PATCH /api/receipts/{id}/note`.

1. **Модель и миграция** — если нужно новое поле или таблица: поле в [app/models.py](app/models.py) и миграция (см. ниже).
2. **Схема** в [app/schemas.py](app/schemas.py):
   ```python
   class ReceiptNoteUpdate(BaseModel):
       note: Optional[str] = Field(default=None, max_length=1000)
   ```
3. **Функция в** [app/crud.py](app/crud.py):
   ```python
   def set_receipt_note(db: Session, receipt: models.Receipt, note: Optional[str]) -> models.Receipt:
       receipt.note = note.strip() if note else None
       db.commit()
       db.refresh(receipt)
       return receipt
   ```
4. **Маршрут в** [server.py](server.py) — в блок с соседними эндпоинтами:
   ```python
   @app.patch("/api/receipts/{receipt_id}/note", response_model=schemas.ReceiptOut, tags=["Receipts"])
   def update_receipt_note(
       receipt_id: int,
       data: schemas.ReceiptNoteUpdate,
       db: Session = Depends(database.get_db),
       current_user: models.User = Depends(auth.get_current_user),
   ):
       """Заметка к своему чеку."""
       receipt = crud.get_receipt_by_id(db, receipt_id=receipt_id, user_id=current_user.id)
       if receipt is None:
           raise HTTPException(status_code=404, detail="Чек не найден")
       return crud.set_receipt_note(db, receipt, data.note)
   ```
5. **Лимит частоты** — если эндпоинт тяжёлый или его можно использовать для перебора: строка в `RATE_LIMIT_RULES` в `server.py`.
6. **Тест** в `tests/`: успех, `401` без токена, `404` для чужого чека, `422` для неверных данных.
7. **Документация** — раздел «Спецификация API» в этом README, в том же PR. Если эндпоинт нужен фронту — договоритесь о формате до реализации.

### Миграции базы данных

Схема меняется **только миграциями Alembic** ([migrations/versions/](migrations/versions/)). `init_db()` применяет их при старте сервера, руками запускать не нужно.

Создать миграцию (из корня проекта, с активированным `.venv`):

```powershell
alembic revision --autogenerate -m "заметка к чеку" --rev-id 0013_receipt_note
```

Затем **обязательно откройте файл и проверьте его**: autogenerate часто ошибается с индексами и типами. Правила:

- `revision` — порядковый номер и короткое имя: `0013_receipt_note`. `down_revision` — предыдущая миграция.
- Миграция должна переживать повторный запуск на базе, где изменение уже есть: перед `add_column`/`create_table`/`create_index` проверяйте через `sa.inspect(bind)` (пример — [0003_budgets.py](migrations/versions/0003_budgets.py)).
- SQLite почти не умеет `ALTER TABLE`: для изменения и удаления колонок используйте `with op.batch_alter_table(...)`. Batch пересоздаёт таблицу через `DROP` старой, поэтому `migrations/env.py` на время миграций выключает в SQLite внешние ключи.
- Если меняется формат существующих данных — переводите и старые строки в той же миграции (пример — даты в [0002_item_category_iso_dates.py](migrations/versions/0002_item_category_iso_dates.py)).
- Тест миграции на отдельной базе: передайте соединение через `cfg.attributes["connection"]` (пример — `TestCategoriesMigration` в [tests/test_categories.py](tests/test_categories.py)).
- Пишите `downgrade()`.

```powershell
alembic current           # текущая ревизия базы
alembic history           # список миграций
alembic upgrade head      # применить все
alembic downgrade -1      # откатить последнюю
```

Перед PR проверьте миграцию на **копии старой базы**: скопируйте `data/checkai.db` в `data/migrate_test.db` и запустите сервер с `DATABASE_URL=sqlite:///data/migrate_test.db` и отдельным `UPLOADS_DIR`.

### Как писать тесты

Тесты — `unittest` + `fastapi.testclient.TestClient`, запускаются через `pytest` (команды — в разделе [Тесты](#тесты)). Временную базу и папки настраивает [tests/testenv.py](tests/testenv.py).

- Первой строкой импортируйте `testenv`, **до** `from server import app`: настройки читаются при импорте.
- `TestClient(app)` без `with` не запускает фоновую очистку фото — так и нужно в тестах.
- Пользователей создавайте прямо через `models.User` и `auth.issue_tokens(user)`, как в [tests/test_budgets.py](tests/test_budgets.py), — быстрее, чем регистрация через API. Такой пользователь создаётся без категорий: если они нужны, вызовите `create_default_categories(db, user)` до `commit`. Готовый базовый класс с двумя пользователями — [tests/apptest.py](tests/apptest.py).
- На каждый эндпоинт: успешный сценарий, `401` без токена, изоляция пользователей (пользователь B получает `404` на объекты A), ошибки валидации (`422`).
- OCR в тестах не запускайте — это долго. Чтобы проверить сохранение распознанного чека, отправляйте готовый JSON в `/api/receipts/save`.
- Прогнать тесты на PostgreSQL — задать `TEST_DATABASE_URL` (базу лучше завести отдельную):
  ```powershell
  $env:TEST_DATABASE_URL = "postgresql://checkai:checkai_secret@localhost:5432/checkai_test"
  python -m pytest tests
  ```

### PostgreSQL

По умолчанию — SQLite. Для PostgreSQL в `docker-compose.yml` есть сервис `db` (профили `postgres` и `full`):

```powershell
# в .env:
# DATABASE_URL=postgresql://checkai:checkai_secret@db:5432/checkai
docker compose --profile postgres up -d
```

Локально без Docker: `DATABASE_URL=postgresql://checkai:checkai_secret@localhost:5432/checkai` при поднятом `docker compose --profile postgres up db`.

- Подмена `lower()` для кириллицы делается только для SQLite. В PostgreSQL `ilike` и так работает с кириллицей.
- В PostgreSQL строже типы: строка не сравнится с числом, `NULL` в `NOT NULL` упадёт сразу.
- Данные из SQLite в PostgreSQL автоматически не переносятся.

### Что ждёт фронтенд

Что важно не сломать в ответах API:

- **Формат ошибок.** Фронт показывает `detail` как есть, если это строка. Если `detail` — список (ошибки валидации `422`), он берёт из каждого элемента `msg` или строит сообщение по полю `loc`.
- **`401` = сессия истекла.** Получив `401`, фронт один раз пробует `POST /api/auth/refresh` и повторяет запрос, при неудаче — переходит в гостевой режим. Не отвечайте `401` на ошибки, не связанные с токеном.
- **`404`/`405` = «сервер этого ещё не умеет».** По этим кодам фронт включает запасное поведение. Новые эндпоинты коллекций должны отвечать `200` и `[]`, а не `404`, когда данных нет.
- **История грузится целиком** порциями по 200 (`GET /api/receipts?skip=&limit=200`) — аналитику, категории и бюджеты фронт считает сам по этим данным. Не уменьшайте максимальный `limit` ниже 200.
- **Поля чека**, которые читает фронт: `id, store, merchant, date, time, category_id, category, total, currency, rate_to_base, source, image_path, created_at, items[{id, name, quantity, price_per_unit, total_price, category_id, category, category_source}]`. Переименование любого из них ломает интерфейс.

### Git и порядок работы

- Основная ветка — `main`. Работайте в отдельной ветке: `feat/<что делаете>`, `fix/<что чините>`.
- Задачи и баги — в GitHub Issues.
- Перед PR: подтянуть `main` (`git fetch origin && git merge origin/main`), прогнать тесты, проверить сервер вручную через `/docs`.
- Сообщения коммитов — с префиксом типа: `feat(backend): …`, `fix(ml): …`, `docs: …`, `test: …`.
- Изменения в API — вместе с обновлением README в том же PR. Новые миграции — с проверкой на копии старой базы.
- **Не коммитьте**: `.env`, `data/*` (база, фото чеков), `*_result.json`, `.venv`. Если файл уже попал в git, `.gitignore` его не уберёт — нужен `git rm --cached <файл>`.
