Составлено 25.11.2026 по состоянию `main` (после PR #30). Задачи для ML-разработчика: ускорить распознавание, поднять точность и научить пайплайн работать с длинными чеками (40–150 позиций) и чеками с большим количеством текста. По каждому пункту: **что** сделать, **где** (файлы), **как** и **зачем**.

Правило команды прежнее: если меняется контракт (поля в ответе `analyze_receipt` / `/api/analyze`), сначала правка в этом файле и сообщение в чат, потом код.

## 0. Главные правила

1. **Каждое изменение — с замером до и после.** Запуск из папки `ml`:
   ```
   python -m evaluation.benchmark --tag before
   # ... изменения ...
   python -m evaluation.benchmark --tag after            # если менялся OCR
   python -m evaluation.benchmark --tag after --reuse-ocr before   # если OCR не менялся (быстрее)
   python -m evaluation.benchmark --compare before after
   ```
   Таблицу сравнения — в описание PR. Без неё PR не принимаем.
2. **Одна идея — один PR.** Иначе непонятно, что дало прирост, а что откатило.
3. **Два модуля OCR.** Сервер вызывает `app/ocr.py`, бенчмарк — `ml/app/ocr.py`. Это две отдельные копии (`init_ocr`, `ocr_image_with_scores`, `analyze_receipt`). Любая правка OCR должна попасть в обе, иначе бенчмарк меряет не то, что работает у пользователя. Лучше сначала сделать задачу [3.0](#30-одна-реализация-ocr-p0).
4. **Запасной путь не ломаем.** Если Ollama недоступна или упала, чек должен разбираться regex-парсером (`app/parser.py`), как сейчас.
5. Тесты: `python -m pytest tests -q` из папки `ml` (Ollama не нужна) и `python -m pytest tests -q` из корня — оба зелёные перед PR.

## 3. Скорость

### 3.0. Одна реализация OCR (P0)

**Где:** `app/ocr.py`, `ml/app/ocr.py`.

**Как:** `app/ocr.py` импортирует `init_ocr`, `ocr_image_with_scores` и `analyze_receipt` из `ml/app/ocr.py` и оставляет у себя только то, что нужно серверу (логи времени этапов, прогрев). Флаги Paddle — в одном месте.

**Зачем:** сейчас правки OCR надо делать дважды, и бенчмарк может мерить не то, что работает в продакшене.

### 3.1. Ускорить OCR: OneDNN или RapidOCR (P1)

**Проблема.** OCR — 62% времени. В `init_ocr()` стоит `enable_mkldnn=False`, а в начале `app/ocr.py` OneDNN выключен ещё и флагами (`FLAGS_use_onednn=0`, `FLAGS_use_mkldnn=0`) — видимо, из-за багов ранних Paddle 3.x. На CPU без OneDNN Paddle работает в разы медленнее.

**Как (по шагам, каждый — с замером):**
1. Сейчас `paddlepaddle==3.2.2`, `paddleocr==3.7.0`. Включить OneDNN (`enable_mkldnn=True`, убрать флаги `*_onednn`/`*_mkldnn`, флаги PIR оставить) и прогнать бенчмарк. Проверить, что результат совпадает (те же строки) и нет падений на всех эталонах.
2. Если OneDNN снова падает — попробовать **RapidOCR** (onnxruntime) с теми же моделями PP-OCRv5. Проверить, есть ли `eslav_PP-OCRv5_mobile_rec` в ONNX; если нет — сконвертировать через `paddle2onnx`. Сравнить скорость и точность распознавания строк с текущим.
3. Поиграть количеством потоков (`cpu_threads` / `OMP_NUM_THREADS`) — на машине с 12 ядрами по умолчанию может использоваться меньше.

**Ожидание:** OCR в 2–4 раза быстрее. Это оценка, нужен замер.

### 3.2. Размер фото перед OCR — по ширине, а не по длинной стороне (P1)

**Где:** `ml/app/preprocess.py`, функция `prepare`.

**Проблема.** Сейчас `OCR_MAX_SIDE=2000` уменьшает фото по **длинной** стороне. Для обычного чека это ок, а длинный чек 1500×6000 превращается в 500×2000 — буквы становятся мелкими, OCR путает цифры в ценах.

**Как:**
- Новый параметр `OCR_TARGET_WIDTH` (подобрать на бенчмарке, ориентир 1000–1200 px): ширину чека приводим к нему, высота — какая получится.
- Если после этого высота больше предела детектора — режем на полосы (задача 5.2), а не уменьшаем всё фото.
- Для обычных чеков проверить, что уменьшение до целевой ширины не ухудшает точность и ускоряет OCR. Подобрать значение по бенчмарку (попробовать 900 / 1100 / 1300).
- Также проверить `text_det_limit_side_len` / `text_det_limit_type` и внутренний предел стороны у детектора PaddleOCR (по памяти — около 4000 px, проверить в документации своей версии): если фото больше, Paddle уменьшит его сам и молча.

**Зачем:** скорость на обычных чеках + читаемость длинных.

### 3.3. Категоризация: Qwen только для незнакомых товаров (P1)

**Где:** `ml/app/categorize.py`, функция `categorize_items`.

**Проблема.** Сейчас Qwen вызывается **на каждом чеке для всех позиций**, а ключевые слова — только если Qwen не справился. Это ~2,9 с на каждый чек, даже если человек в десятый раз покупает тот же хлеб. Таймаут запроса — 30 с: на длинном чеке он может не уложиться.

**Как — новый порядок:**
1. **Правила пользователя** (`category_rules`: пользователь переносил товар в категорию — запомнили). Уточнить у бэка, применяются ли они сейчас до ML или после; если после — передавать их в `categorize_items` и применять первыми.
2. **Кэш по нормализованному названию** (`normalize_item_name` уже есть): `название → категория` для этого пользователя или общий для стандартных категорий. Хранить в БД (договориться с бэком) или в памяти процесса с ограничением размера.
3. **Ключевые слова** (`_match_by_keywords`) — только если совпадение уверенное.
4. **Qwen** — одним запросом только для позиций, которые не определились на шагах 1–3.

Метрику «категории верные» и время категоризации сравнить до/после. Добавить в `category_source` значения `"rule"` и `"cache"` (см. раздел 6).

**Альтернатива для исследования (P2):** просить категорию сразу в промпте разбора чека (один вызов LLM вместо двух). Сравнить точность — модель 3b может путаться от двойной задачи.

### 3.4. Настройки Qwen (P1)

**Где:** `ml/app/agent_parser.py` (`_call_llm`, `SYSTEM_PROMPT`), `ml/app/llm.py`.

- **JSON-схема вместо `format="json"`.** Ollama принимает в `format` JSON-схему ответа — модель не сможет выдать лишние поля или сломанную структуру. Описать схему чека один раз и использовать в разборе и самокоррекции.
- **Сократить промпт.** Сейчас `SYSTEM_PROMPT` — около 3,4 тыс. символов. Примеры вынести в отдельный файл, убрать повторы, проверить на бенчмарке, что точность не упала. Короче промпт — быстрее обработка и больше места под текст чека.
- **Служебные строки вырезать до LLM** (см. 5.5).
- **Таймаут и попытки:** сейчас `ollama.Client(timeout=120)` в разборе и `timeout=30` в категоризации. Сделать их зависящими от длины чека (5.3) и вынести в переменные окружения.
- `keep_alive="30m"` и одинаковый `num_ctx` в разборе и категоризации — оставить (иначе Ollama перезагружает модель).

### 3.5. Самокоррекция — реже и дешевле (P2)

**Где:** `needs_correction`, `self_correction` в `agent_parser.py`.

Сейчас второй вызов LLM идёт при любом расхождении суммы позиций с итогом больше 0,01. После задачи 4.1 (склейка строк) расхождений должно стать меньше. Замерить, в какой доле чеков самокоррекция срабатывает и как часто **реально исправляет** (`_should_accept_correction`). Если почти никогда — исправлять только расходящиеся позиции, а не перегенерировать весь чек.

## 4. Точность

### 4.1. Склейка фрагментов OCR в строки по координатам (P1, главный рычаг)

**Где:** `ocr_image_with_scores` в `ml/app/ocr.py` (и `app/ocr.py` до задачи 3.0).

**Проблема.** Сейчас берутся только `rec_texts` в порядке, в котором их отдал Paddle; координаты (`rec_boxes` / `rec_polys`) не используются. На чеке «Молоко 3,2% ........ 2 x 450 = 900» Paddle часто находит 2–3 отдельных фрагмента, и в Qwen они приходят **разными строками**. Модель гадает, какая цена к какому товару относится, отсюда расхождение суммы позиций с итогом в 47% чеков.

**Как:**
1. Взять у каждого фрагмента рамку, посчитать центр по вертикали и высоту.
2. Фрагменты, у которых центры по вертикали отличаются меньше чем на ~0,5 высоты строки, — одна строка. Внутри строки сортировать по X, соединять пробелом (или ` | ` для явных колонок — проверить, что лучше понимает Qwen).
3. Учесть наклон фото: если чек снят под углом, строка «плывёт» по Y. Для начала — оценить средний наклон по рамкам и компенсировать.
4. Уверенность строки — минимум (или среднее) по фрагментам.
5. Сохранить старый режим за переменной `OCR_MERGE_LINES=0` для сравнения.

**Проверка:** `sum_matches_total`, `item_recall`, `item_precision` до и после. Ожидаем заметный рост.

### 4.2. Уверенность по позициям (P1)

**Где:** `ml/app/confidence.py`.

Сейчас `compute_confidence` считает уверенность по чеку. Добавить уверенность **по каждой позиции** (`item.confidence`, 0–1): уверенность OCR строк, из которых взята позиция, + сходится ли `quantity × price = total`, + нашлись ли числа позиции в OCR-тексте (`is_item_confirmed` уже есть). Фронт подсветит сомнительные позиции — пользователь проверит их, а не весь чек. **Меняет контракт** — см. раздел 6.

### 4.3. Сравнение моделей на новом наборе (P2)

После задачи 2.1 сравнить на бенчмарке: `qwen2.5:3b` (сейчас), `qwen2.5:7b`, более новые небольшие модели, доступные в Ollama. Таблица: точность по группам short/long, p50/p95 времени, потребление памяти. Выбрать модель по умолчанию; если 7b заметно точнее, но медленнее — оставить выбор через `OLLAMA_MODEL`.

### 4.4. Данные чека по QR-коду ОФД (P2, исследование)

**Где:** `ml/app/fiscal.py` (сейчас ищет QR-ссылку только в распознанном **тексте**).

**Идея.** На фискальных чеках Казахстана есть QR со ссылкой на чек в ОФД. Если декодировать QR прямо с фото (`cv2.QRCodeDetector` или `pyzbar`) и получить данные чека с сайта ОФД — позиции, суммы, магазин и дата будут точными, без OCR и LLM, за секунды.

**Что выяснить и сделать:**
1. Какие ОФД встречаются на наших чеках, какой формат ссылок, отдаёт ли страница данные без капчи, разрешено ли автоматическое получение (условия использования).
2. Прототип: фото → QR → ссылка → данные чека в нашем формате.
3. В пайплайне: если QR найден и данные получены — используем их (`parser_used = "ofd"`), иначе обычный путь. OCR при этом можно запускать параллельно как запасной.

Решение, включать ли это в продукт, — за PM (внешний запрос, зависимость от сайтов ОФД).

### 4.5. Запасной разбор трудных чеков через Gemini (P2, нужно решение PM)

`ml/app/llm.py` уже умеет вызывать Gemini. Для чеков с низкой уверенностью можно отправлять **фото** в Gemini Flash (модель с распознаванием изображений) и сравнивать результат. Минус: фото чека уходит во внешний сервис — нужно согласие пользователя и решение PM. Сначала замерить на эталонах, насколько это точнее.

## 5. Длинные чеки и чеки с большим количеством текста

### 5.0. Что сломается сейчас (по коду)

| Этап | Проблема | Где |
|---|---|---|
| Предобработка | Фото уменьшается по длинной стороне до 2000 px — длинный чек становится нечитаемо мелким | `preprocess.py`, `OCR_MAX_SIDE` |
| OCR | Внутренний предел стороны у детектора Paddle — очень высокое фото уменьшается ещё раз | `init_ocr` |
| Qwen: ответ | `num_predict: 2048` — JSON на 60–100 позиций не помещается, ответ обрезается, `json.loads` падает → откат на regex | `_call_llm` в `agent_parser.py` |
| Qwen: контекст | `num_ctx=8192` = промпт (~2 тыс. токенов) + текст чека (3–5 тыс.) + ответ (3–5 тыс.). При переполнении Ollama **молча отрезает начало** — теряются инструкции или шапка чека | `NUM_CTX` |
| Qwen: время | 3b на CPU генерирует несколько тысяч токенов дольше `timeout=120`; с самокоррекцией — два таких вызова | `_call_llm` |
| Категоризация | Все позиции одним запросом с `timeout=30` — на 100 позициях не уложится | `categorize.py` |
| Служебный текст | Реклама, бонусы, реквизиты ОФД раздувают вход модели и время, позиций не добавляют | — |

### 5.1. Признак «длинный чек» (P0)

Функция `receipt_size(lines, image_shape) -> "short" | "long"`: по числу OCR-строк (ориентир > 80) и/или соотношению сторон фото (высота / ширина > 3). Порог подобрать на эталонах. От этого признака зависят задачи 5.2–5.4.

### 5.2. OCR длинного фото полосами (P1)

**Где:** `ml/app/preprocess.py` + `ocr_image_with_scores`.

1. Ширину привести к целевой (задача 3.2).
2. Если высота больше предела детектора — резать на горизонтальные полосы (ориентир — 1600 px) **с перекрытием** (~100–150 px, больше высоты двух строк).
3. OCR каждой полосы, координаты фрагментов перевести в координаты всего фото.
4. Строки из зоны перекрытия, найденные в обеих полосах, — убрать дубли (по координате Y и похожести текста).
5. Дальше — обычная склейка строк (4.1).

**Бонус:** полосы можно обрабатывать по очереди и сообщать прогресс (5.6).

### 5.3. Параметры LLM от длины чека (P0)

**Где:** `_call_llm` в `agent_parser.py`, `categorize_via_qwen`.

- `num_predict` — от числа строк/предполагаемых позиций (с запасом), а не фиксированные 2048.
- `num_ctx` — так, чтобы помещались промпт + текст + ответ. **Важно:** разный `num_ctx` заставляет Ollama перезагружать модель. Поэтому не считать его точно на каждый чек, а держать 2–3 фиксированных значения (например, 8192 для обычных и 16384 для длинных) и проверить, сколько времени занимает переключение.
- Таймаут — от длины чека.
- Проверять `done_reason` в ответе Ollama: если `"length"` — ответ обрезан. Логировать и переходить к разбору кусками (5.4), а не к regex.

### 5.4. Разбор длинного чека кусками (P1)

**Где:** новая функция в `agent_parser.py`, например `parse_long_receipt(ocr_text)`.

1. **Шапка** (первые ~15 строк): магазин, дата, время, валюта — отдельный короткий запрос (или regex + `canonical_merchant`).
2. **Итог** — из конца чека (`extract_total_from_ocr` уже есть).
3. **Позиции** — блоками по 30–40 строк с перекрытием в 2–3 строки (чтобы не разрезать позицию «название / кол-во × цена» пополам). Каждый блок — отдельный запрос «верни только позиции».
4. Склеить, убрать дубли на стыках, применить `finalize_receipt_items`.
5. Сверить сумму позиций с итогом; если не сходится — самокоррекцию запускать **только для блока**, где вероятнее ошибка, а не для всего чека.
6. Блоки можно отправлять параллельно, если Ollama настроена на несколько параллельных запросов (`OLLAMA_NUM_PARALLEL`) — замерить, есть ли выигрыш на CPU.

### 5.5. Компактный ответ и вырезание служебного текста (P1)

- **Компактный формат позиций в ответе модели:** массив `["Молоко 3,2%", 2, 450, 900]` вместо объекта с ключами `name/quantity/price_per_unit/total_price`. Ответ короче примерно вдвое → быстрее генерация и меньше шанс обрезки. В коде сразу преобразовывать обратно в объекты — **контракт наружу не меняется**.
- **Служебные строки — до LLM.** `normalize_service_text` и `is_service_item` сейчас применяются к результату. Применять и к OCR-тексту **перед** отправкой в Qwen: реклама, бонусы, условия возврата, реквизиты ОФД (их отдельно разбирает `extract_fiscal_info` — ему передавать полный текст). Осторожно: не выкинуть позиции. Проверить на эталонах, что `item_recall` не упал.

### 5.6. Гибрид: regex для простых строк, Qwen для сложных (P2)

Многие строки позиций имеют стандартный вид («название … кол-во × цена = сумма» или «название / 2 x 450 / 900»). Их надёжно разбирает регулярное выражение — быстро и без ошибок модели. В Qwen отправлять только строки, которые regex не понял, + шапку. На длинных чеках это может сократить работу модели в разы. Сравнить точность с чистым Qwen на группе `long`.

### 5.7. Несколько фото одного чека (P1, вместе с бэком и фронтом)

Длинный чек пользователь снимает 2–3 кадрами сверху вниз.

**ML:** функция `merge_pages(pages: List[List[str]]) -> List[str]`: склейка **распознанного текста**, не картинок. На стыке соседних кадров найти совпадающие строки (по похожести, `difflib`) и убрать повторы. Если общих строк не нашлось — просто соединить по порядку и вернуть предупреждение (см. раздел 6). Дальше обычный разбор.

**Бэк/фронт:** `/api/analyze` и `/api/analyze/async` принимают несколько файлов — контракт согласовать отдельно (раздел 6).

### 5.8. Прогресс для длинных чеков (P2)

`analyze_receipt` принимает необязательный `on_progress(stage: str, done: int, total: int)` и вызывает его по ходу: OCR полос, блоки LLM, категоризация. Бэк прокидывает это в `app/tasks.py`, фронт показывает «Распознано 2 из 4 частей» через `/api/tasks/{task_id}`.
