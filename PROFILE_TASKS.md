## 0. Что сделал фронтенд

| Что | Где видно | Откуда данные сейчас | Что не так |
|---|---|---|---|
| Обложка: фото, имя, email, «с нами с …», валюта | Профиль, верх | `GET /api/auth/me` | Фото — только в `localStorage` (→ 1.1) |
| Цифры: чеков, потрачено, средний чек, дней с нами | Профиль | Фронт считает по **всем** чекам | Качает всю историю (→ 1.3) |
| Тепловая карта активности за 26 недель | Профиль | Фронт считает по всем чекам | То же (→ 1.3) |
| Привычки: любимый магазин, топ-категория, крупнейший чек, месяц к прошлому | Профиль | Фронт считает | Магазины не склеиваются (→ 2.2) |
| Первые шаги | Профиль | `me`, чеки, `/api/budgets`, `/api/category-rules` | — |
| Вкладка «Личное»: имя, основная валюта | Настройки | `PATCH /api/auth/me` | После смены валюты суммы временно занижены (→ 1.6) |
| Вкладка «Вход и пароль»: email, пароль с оценкой надёжности | Настройки | `PATCH /api/auth/me` | — |
| Вкладка «Аккаунты» | Настройки | `localStorage` | Нет «выйти везде» (→ 1.4) |
| Вкладка «Оформление»: тема + **акцентный цвет** | Настройки | `localStorage` | Не синхронизируется между устройствами (→ 1.2) |
| Вкладка «Данные»: выгрузка JSON / CSV | Настройки | Фронт собирает сам | Без фото чеков (→ 1.5) |
| Вкладка «Удаление» | Настройки | `DELETE /api/auth/me` | — |
| **Фото профиля**: загрузка с устройства, снимок камерой, кадрирование | Профиль, шапка, меню аккаунтов | `localStorage` | Нет на сервере (→ 1.1) |
| Кнопка темы на лендинге | Главная для гостя | `localStorage` | — |

Контракт `PATCH` и `DELETE /api/auth/me` **не менялся**. Фронт просто отправляет личные данные и данные входа двумя отдельными запросами.

## 1. Бэкенд

### 1.1. Аватар на сервере — **высокий приоритет**

**Зачем.** Интерфейс фото уже готов, и пользователи будут им пользоваться. Сейчас фото лежит в `localStorage` браузера: на телефоне его не видно, после очистки данных сайта оно пропадает.

**Что уже делает фронт.** Пользователь выбирает файл или снимает камерой, двигает и масштабирует кадр. Фронт сам режет картинку в **квадрат 256×256 JPEG (качество 0.88, обычно 15–40 КБ)**. То есть на сервер придёт уже маленький готовый файл, и ресайз на бэке не обязателен.

#### Что сделать

**1) Модель** — `app/models.py`, класс `User`:

```python
avatar_path = Column(String(500), nullable=True)  # "/avatars/<uuid>.jpg"
```

**2) Миграция** — `migrations/versions/0006_avatar.py`, `down_revision = "0005_categories"`:

```python
op.add_column("users", sa.Column("avatar_path", sa.String(500), nullable=True))
```

Сразу под 1.2 можно в той же миграции добавить `preferences`, чтобы не плодить миграции.

**3) Конфиг** — `app/config.py`, по образцу `UPLOADS_DIR`:

```python
AVATARS_DIR = os.getenv("AVATARS_DIR", "").strip() or os.path.join(DATA_DIR, "avatars")
AVATARS_URL_PREFIX = "/avatars"
MAX_AVATAR_BYTES = 2 * 1024 * 1024
```

**4) Раздача файлов** — `server.py`, рядом с `app.mount(RECEIPTS_URL_PREFIX, ...)`:

```python
os.makedirs(config.AVATARS_DIR, exist_ok=True)
app.mount(config.AVATARS_URL_PREFIX, StaticFiles(directory=config.AVATARS_DIR), name="avatars")
```

Важно: монтировать **только** `data/avatars`, а не `data/` целиком, потому что там лежит `checkai.db`. Так уже сделано для чеков.

**5) Схема** — `app/schemas.py`, `UserOut`:

```python
avatar_url: Optional[str] = None
```

Заполнять из `avatar_path`, например через `@computed_field` или `validation_alias="avatar_path"`. **Имя поля в ответе именно `avatar_url`**: фронт его уже читает (`avatarSrc` в `app.js`).

**6) Эндпоинты** — `server.py`, секция «Аутентификация»:

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| `POST` | `/api/auth/me/avatar` | `multipart/form-data`, поле `file` | `UserOut` |
| `DELETE` | `/api/auth/me/avatar` | — | `UserOut` с `avatar_url: null` |

Что делает `POST`:
1. Проверяет размер (≤ 2 МБ) и тип: `image/jpeg`, `image/png`, `image/webp`. Тип проверять **по содержимому**, а не по `Content-Type`. Можно через Pillow: `Image.open(...).verify()`. Pillow уже ставится вместе с PaddleOCR, но его стоит явно указать в `requirements.txt`.
2. Сохраняет файл как `data/avatars/<uuid4().hex>.jpg`. Имя каждый раз **новое**: тогда браузер не покажет старое фото из кэша, и параметр `?v=` не понадобится.
3. Удаляет старый файл пользователя, если он был.
4. Пишет `avatar_path`, делает `commit` и возвращает `UserOut`.

Что делает `DELETE`: удаляет файл, ставит `avatar_path = None` и возвращает `UserOut`.

**7) Удаление аккаунта** — `DELETE /api/auth/me` в `server.py` и `crud.delete_user`. Вместе с пользователем удалять и файл аватара. Сейчас `delete_user` возвращает только `image_paths` чеков. Можно добавить в него `avatar_path` или удалять файл прямо в `delete_me`.

**8) Тесты** — `tests/test_avatar.py`:
- загрузка → `avatar_url` в `GET /api/auth/me`;
- повторная загрузка → старый файл удалён;
- файл > 2 МБ → 413 или 400;
- текстовый файл с расширением `.jpg` → 400;
- `DELETE` → поле `null`, файла нет;
- удаление аккаунта → файла нет;
- чужой пользователь не может удалить ваш аватар (у эндпоинта просто нет `user_id` в пути).

**Ошибки** — как везде, `{"detail": "текст по-русски"}`. Фронт покажет `detail` в окне фото.

### 1.2. Настройки оформления в аккаунте

**Зачем.** Пользователь выбрал «светлая + красный» на ноутбуке, открыл сайт на телефоне, а там снова тёмная фиолетовая. Сейчас тема и акцент хранятся в `localStorage` (ключи `checkai_theme` и `checkai_accent`).

**Приоритет средний.** Без этого всё работает, просто без синхронизации.

#### Что сделать

**1) Модель** — `User` в `app/models.py`:

```python
preferences = Column(JSON, nullable=False, default=dict, server_default="{}")
```

Миграцию можно объединить с 1.1 в `0006`.

**2) Схемы** — `app/schemas.py`:

```python
class Preferences(BaseModel):
    theme: Literal["dark", "light", "system"] = "system"
    accent: Literal["violet", "red", "orange", "green", "blue", "pink"] = "violet"
```

- В `UserOut` добавить `preferences: Preferences = Preferences()`.
- В `UserUpdate` добавить `preferences: Optional[Preferences] = None`.

**3) `PATCH /api/auth/me`** — в `update_me` в `server.py`: если `"preferences" in user_data.model_fields_set`, сохранить `user_data.preferences.model_dump()`. Текущий пароль для этого **не нужен**: это не данные входа.

**Список значений.** Если добавите новый цвет, это делается только вместе с фронтом: палитра каждого цвета прописана в `frontend/static/css/app.css` (блок «Акцентные цвета»). Неизвестное значение должно давать 422, а не молча сохраняться.

### 1.3. Сводка профиля одним запросом — **высокий приоритет**

**Зачем.** Чтобы показать цифры, тепловую карту и привычки, фронт выкачивает **всю** историю пачками (`fetchAllReceipts` в `app.js`, `GET /api/receipts?skip=…&limit=…`). При 500 чеках это несколько запросов и мегабайты JSON на телефоне. К тому же правила «какая дата у чека» и «как пересчитать в основную валюту» живут и на фронте, и на бэке, и могут разойтись.

#### Что сделать

`GET /api/profile/stats?tz=Asia/Almaty`. Все суммы — в основной валюте пользователя, с тем же пересчётом, что в `crud.attach_base_rates` и `/api/analytics`.

```json
{
  "base_currency": "KZT",
  "receipts_count": 148,
  "items_count": 1203,
  "total_spent": 1843200.0,
  "average_receipt": 12454.05,
  "unconverted": [{ "currency": "USD", "count": 2 }],
  "first_receipt_at": "2026-03-12",
  "last_receipt_at": "2026-11-03",
  "activity": [{ "date": "2026-11-03", "count": 2, "total": 8420.0 }],
  "longest_streak": 6,
  "top_weekday": 5,
  "top_store": { "name": "Magnum", "count": 31 },
  "top_category": { "id": 4, "total": 412000.0 },
  "biggest_receipt": { "id": 87, "total": 64300.0, "store": "Technodom" },
  "month_total": 152000.0,
  "prev_month_total": 171500.0
}
```

Правила, иначе цифры на фронте и в ответе разойдутся:

- **Дата чека** = `receipts.date`, а если её нет — `created_at`, переведённый в часовой пояс `tz`. Так считает фронт (`receiptIso`).
- **`activity`** — последние 182 дня (26 недель), только дни, в которые были чеки.
- **`tz`** — IANA-имя, фронт передаст `Intl.DateTimeFormat().resolvedOptions().timeZone`. Если параметра нет — UTC.
- **`top_weekday`**: 0 = воскресенье … 6 = суббота, как `Date.getDay()` в JS.
- **`average_receipt`** — делить на число **пересчитанных** чеков, а не на всё количество.
- **`top_store`** — группировать без учёта регистра и пробелов по краям. Когда появится `merchant` (2.2), группировать по нему.
- Чеки без курса не входят в суммы, но перечисляются в `unconverted`, как в `AnalyticsOut`.

Считать лучше SQL-агрегатами в `app/crud.py`, а не загружать все строки в Python.

### 1.4. «Выйти на всех устройствах»

**Сейчас.** Токены пользователя отзываются только при смене пароля: в токене лежит claim `pwd` = `password_fingerprint(user)`, см. `app/auth.py`.

**Зачем.** Потерял телефон — нужна кнопка «выйти везде» без смены пароля. На вкладке «Аккаунты» для неё уже есть место.

#### Что сделать

1. Добавить `users.token_version` (Integer, default 0).
2. В `app/auth.py` включить версию в claims (рядом с `pwd`) и проверять её в `get_current_user` и при refresh.
3. `POST /api/auth/logout-all` → `token_version += 1` → вернуть `TokenOut` (новую пару токенов для текущего устройства, через `_token_response`).

По желанию: `GET /api/auth/sessions` — устройство (User-Agent), IP, время последнего входа.

### 1.5. Полная выгрузка данных (ZIP)

**Сейчас.** На вкладке «Данные» фронт собирает JSON из того, что уже загрузил: чеки, категории, правила, лимиты. **Фото чеков туда не попадают**, в интерфейсе об этом есть пометка.

**Зачем.** Пользователь должен иметь возможность забрать всё своё, в том числе по требованиям закона о персональных данных.

**Что сделать.** `GET /api/auth/me/export` → `application/zip`:

- `data.json`: `{ exported_at, user, receipts, categories, category_rules, budgets }` — тот же состав, что выгружает фронт;
- `images/<имя файла>` — фото чеков;
- `avatar.jpg`, если есть (1.1).

Собирать через `zipfile` в стриминговом ответе (`StreamingResponse`), не держа весь архив в памяти.

### 1.6. Смена основной валюты и курсы

**Сейчас.** После `PATCH /api/auth/me` с новой `base_currency` сервер докачивает курсы в фоне (`rates.run_in_background(crud.backfill_user_rates, ...)` в `update_me`). Фронт сразу перезапрашивает чеки, и часть из них уходит в «не учтено — нет курса». Пользователь видит заниженную сумму в профиле и не понимает почему.

**Что сделать.**
- В `UserOut` добавить `rates_pending: bool`: `true`, пока фоновая задача для этого пользователя не закончилась. Можно хранить в памяти множество `user_id`, как сейчас устроен `rates.run_in_background`, или в колонке.
- Флаг отдаётся и в ответе `PATCH`, и в `GET /api/auth/me`.

Фронт по флагу покажет «Пересчитываем по новому курсу…», будет опрашивать `GET /api/auth/me` и перерисует цифры, когда флаг станет `false`.

### 1.7. Сброс пароля по письму

**Сейчас.** `POST /api/auth/forgot-password` отдаёт `reset_token` прямо в ответе. Для продакшена это дыра: кто угодно может сбросить чужой пароль, зная email.

**Что сделать.**
- Отправлять письмо со ссылкой `https://<домен>/?reset=<token>` и **не** возвращать токен в ответе.
- Ответ всегда одинаковый, даже если такого email нет: `{"success": true}`. Так не получится узнать, кто зарегистрирован.
- SMTP-настройки — в `.env` и `app/config.py`. В `.env.example` добавить пустые переменные.

Фронт добавит форму «Забыли пароль?» и экран нового пароля по ссылке `?reset=`.

---

### 1.8. Мелочи (низкий приоритет)

- **`last_login_at`** в `users`, обновлять в `/api/auth/login` и отдавать в `UserOut`. Тогда в профиле появится «последний вход».
- **Подтверждение email.** Если появится, отдавать `email_verified: bool`, и в обложке будет бейдж.

## 2. ML

### 2.1. Источник категории до самой базы

**Зачем.** ML уже отдаёт у позиции `category_source`, и фронт показывает его в редакторе до сохранения («ИИ определил», «по ключевым словам», «по вашему правилу»). Но после сохранения источник теряется: его нет ни в `ItemIn`, ни в модели, ни в `ItemOut`. Поэтому нельзя ни показать в профиле «ИИ сам разложил 82% позиций, вы поправили 14», ни измерить качество категоризации на реальных данных.

**Где источник появляется сейчас:**
- `ml/app/categorize.py`: `'ai' | 'keywords' | None`;
- `app/categories.py`: `'rule'`, правило пользователя важнее ML;
- `server.py`, `_run_ocr` / `_analyze`: пробрасывает `category_source` в ответ.

#### ML

1. Гарантировать, что `category_source` есть у **каждой** позиции, в том числе в асинхронном пути `/api/analyze/async` → `/api/tasks/{id}`.
2. Не оставлять `None` без причины. Если категория не определилась, пусть будет `None` + `category_id: null`. Если определилась, источник должен быть указан всегда.
3. Добавить в `ml/tests/test_categorize.py` проверку, что поле есть у всех позиций.

#### Бэкенд

1. **Модель** `ReceiptItem` (`app/models.py`): `category_source = Column(String(16), nullable=True)`, миграция.
2. **`ItemIn`** (`app/schemas.py`): `category_source: Optional[Literal["ai", "keywords", "rule", "user"]] = None`. Фронт начнёт его отправлять в `/api/receipts/save` и `PUT /api/receipts/{id}`.
3. **`ItemOut`**: отдавать `category_source`.
4. **`crud.create_receipt` и обновление чека**: сохранять пришедшее значение.
5. **`POST /api/items/move`** (`crud.move_items`): при ручном переносе ставить `category_source = "user"`.

| Значение | Когда |
|---|---|
| `ai` | Категорию выбрала модель |
| `keywords` | Сработали ключевые слова (запасной путь ML) |
| `rule` | Сработало правило пользователя (`category_rules`) |
| `user` | Пользователь сам выбрал или перенёс |
| `null` | Категории нет |

---

### 2.2. Каноническое имя магазина

**Зачем.** «Любимый магазин» в профиле и поиск в истории группируются по строке `store`. OCR пишет одну и ту же сеть по-разному: «MAGNUM», «Magnum Cash&Carry», «ТОО "Magnum"», «МАГНУМ». В итоге статистика размазывается, и любимым оказывается не тот магазин.

#### ML (`ml/app/parser.py` → `find_store_name`, `ml/app/agent_parser.py`)

Возвращать рядом со `store` поле **`merchant`** — короткое каноническое имя сети:
- без организационно-правовой формы (ТОО, ИП, АО, LLP, ООО) и кавычек;
- без адреса и номера филиала;
- в одном регистре и одной раскладке: «Magnum», а не «МАГНУМ».

`store` оставить как есть: это то, что напечатано на чеке.

Хорошо бы иметь словарь известных сетей (Magnum, Small, Galmart, Technodom, Sulpak, Арбуз…) плюс эвристику для остальных. Добавить тест на варианты из примера выше.

#### Бэкенд

- `receipts.merchant` (String 255, nullable) + миграция;
- поле в `ReceiptCreate`, `ReceiptUpdate`, `ReceiptOut`;
- поиск `q` в `GET /api/receipts` — и по `merchant` тоже;
- `top_store` в 1.3 — по `merchant`, а если его нет — по `store`.

Фронт будет показывать `merchant`, если он есть, и группировать по нему.

### 2.3. Уверенность распознавания (по желанию)

Если ML может отдавать общую `confidence` по чеку (0–1), например среднюю уверенность PaddleOCR по строкам и долю сошедшихся сумм:

- бэкенд хранит её в `receipts.confidence` и отдаёт в `ReceiptOut`;
- фронт подсветит в истории чеки с низкой уверенностью («проверьте») и покажет в профиле среднюю точность.
