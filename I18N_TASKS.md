## 0. Главные правила: чтобы ничего не сломалось

Прочитать всем до начала работы.

1. **Без выбора языка всё работает как сейчас.** Запрос без заголовка `Accept-Language`, пользователь без `preferences.language`, браузер без сохранённого языка получают русский сайт и русские ответы API, **слово в слово** как сегодня. Поэтому существующие тесты (`tests/`, `ml/tests/`) должны проходить **без единой правки ожиданий**. Если старый тест пришлось поменять, значит сломано поведение. Нужно остановиться и написать в чат.
2. **Переводим только то, что видит человек. Данные не трогаем.** В базе, в JSON API, в `localStorage` и в экспорте JSON ничего не переименовываем: названия полей, значения `source`, `category_source`, `type`, `kind`, `theme`, `accent`, ключи `localStorage`, `id` и классы в HTML, `value` у `<option>` остаются прежними.
3. **Логика не зависит от переведённого текста.** Нигде нельзя сравнивать строку из интерфейса или из `detail` ошибки, например `if (name === 'Без категории')` или `detail.includes('Чек не найден')`. Сравнивать можно только коды, `id` и ключи.
4. **Категории в базе остаются на русском.** Стандартные категории получают стабильный ключ `default_key` (п. 3.2), по нему фронт показывает перевод. ML продолжает получать русские названия и описания, поэтому качество категоризации не меняется.
5. **Сначала рефакторинг, потом перевод.** Фронт и бэк сначала выносят русские строки в словари без изменения поведения: отдельный PR, после которого сайт выглядит **точно так же**. Только потом добавляются `kk` и `en`. Так проще найти, что сломалось.
6. **Отсутствующий перевод не ломает экран.** Если ключа нет в `kk` или `en`, показывается русский текст, а не пустота и не `undefined`.
7. **OCR-модель и параметры распознавания на этой неделе не меняем.** Язык интерфейса не связан с языком чека. Казахский чек распознаётся так же, как сейчас.
8. **Казахские тексты проверяет носитель языка** (п. 5.6) до слияния в `main`. Машинный перевод без проверки не выкладываем.

## 1. Общие решения для всех

### 1.1. Коды языков и как выбирается язык

| Код | Язык | В переключателе | Локаль для `Intl` |
|---|---|---|---|
| `ru` | Русский | `РУС` / «Русский» | `ru-RU` |
| `kk` | Қазақша | `ҚАЗ` / «Қазақша» | `kk-KZ` |
| `en` | English | `ENG` / «English» | `en-US` |

- Код всегда в нижнем регистре, ровно эти три значения. Синоним `kz` принимается на входе (фронт, бэк) и приводится к `kk`. Хранится и отдаётся только `kk`.
- **Язык по умолчанию — `ru`.**
- **Порядок выбора языка на фронте:**
  1. Пользователь вошёл и у него задан `preferences.language` → этот язык.
  2. Иначе язык из `localStorage['checkai_lang']`.
  3. Иначе язык браузера `navigator.languages`: первый, который начинается на `kk`/`kz`, `ru` или `en`.
  4. Иначе `ru`.
- Выбор языка вошедшим пользователем сохраняется **и** в `localStorage`, **и** на сервере (`PATCH /api/auth/me`, `{"preferences": {"language": "kk"}}`). Гость сохраняет язык только в `localStorage`. При входе гостя: если на сервере язык не задан (`null` / по умолчанию), а гость уже выбрал язык, фронт отправляет его на сервер, чтобы выбор не пропал.
- **Как бэк узнаёт язык:** заголовок `Accept-Language`. Фронт **всегда** явно ставит `Accept-Language: ru|kk|en` во всех запросах (`fetch` и XHR загрузки). Нет заголовка или неизвестный язык → `ru`.

### 2.1. Механизм переводов: `i18n.js`

**Зачем:** один простой механизм без сборщика и без библиотек: у нас обычный JS без бандлера.

**Где:** новые файлы
- `frontend/static/js/i18n.js` — ядро;
- `frontend/static/js/locales/ru.js`, `kk.js`, `en.js` — словари.

**Как:**
- Словарь — плоский объект с ключами через точку: `window.CHECKAI_LOCALES = window.CHECKAI_LOCALES || {}; CHECKAI_LOCALES.ru = { 'nav.history': 'История', ... }`.
- Ключи группируем по экранам: `common.*`, `nav.*`, `auth.*`, `upload.*`, `editor.*`, `history.*`, `receipt.*`, `categories.*`, `analysis.*`, `budget.*`, `insights.*`, `profile.*`, `duplicates.*`, `errors.*`, `cat.*` (стандартные категории), `currency.*`. Ключ называет смысл, а не текст: `history.empty`, а не `history.netChekov`.
- API ядра:
  - `t(key, params)` — перевод с подстановкой `{name}`: `t('receipt.saved', { store: 'Magnum' })`. Подставляемые значения экранируются там же, где и раньше (`esc`), если идут в `innerHTML`.
  - `tp(key, n, params)` — множественное число через `Intl.PluralRules(locale)`. В словаре хранятся формы `key.one`, `key.few`, `key.many`, `key.other`. Для `ru` нужны `one/few/many`, для `en` — `one/other`, для `kk` — `one/other` (по CLDR, по смыслу формы одинаковые). Если нужной формы нет, берётся `other`, затем `many`. **Текущая функция `plural()` (`app.js`, строка 32) заменяется на `tp`** во всех местах вызова.
  - `getLang()`, `setLang(code)`, `locale()` → `ru-RU` / `kk-KZ` / `en-US`.
  - `applyStaticTranslations(root = document)` — проходит по атрибутам (п. 2.3).
- Запасной вариант: ключа нет в текущем языке → берём из `ru` и пишем `console.warn` один раз на ключ. Ключа нет и в `ru` → возвращаем сам ключ, чтобы ошибку было видно сразу.
- Подключение в `index.html` **до** `app.js`, тоже с `defer` и тем же `?v=`: `locales/ru.js`, `locales/kk.js`, `locales/en.js`, `i18n.js`, затем `app.js`. При любом изменении словарей поднимать `?v=` у всех скриптов, иначе браузер покажет старый перевод из кэша.
- В inline-скрипт в `<head>` (строка 8, где выставляется тема) добавить выставление `document.documentElement.lang` из `localStorage['checkai_lang']`, чтобы не было мигания языка.

### 2.2. Шаг 1 — вынести русский текст в `ru.js` (отдельный PR, поведение не меняется)

**Зачем:** правило 0.5. После этого PR сайт выглядит **точно так же**, а тестировщик сравнивает скриншоты «до/после» (п. 5.2).

**Как:**
- Каждая русская строка в `app.js` → вызов `t('…')`, исходный текст переносится в `ru.js` **без изменений**: те же знаки, кавычки «ёлочки», неразрывные пробелы, `≈`, `₸`.
- Таблицы со строками, например `CATEGORY_SOURCE_TEXT` (строка 126), `UNCATEGORIZED.name` (строка 121), тексты шагов OCR, тексты пустых состояний, превращаются в **функции** или получают текст через `t()` в момент отрисовки. Нельзя вычислять текст один раз при загрузке скрипта, иначе после смены языка останется старый.
- `UNCATEGORIZED` остаётся объектом с `id: null`. Поле `name` для логики больше не используется, отображение идёт через `categoryName(c)` (п. 2.5).
- Длинные HTML-шаблоны в `app.js`: переводятся только текстовые части, разметка не меняется.
- Готовность: `grep` по `app.js` не находит кириллицы в строковых литералах (комментарии можно оставить). Скрипт проверки — п. 2.10.

### 2.3. Статический текст в `index.html`

**Как:** атрибуты-разметка, `applyStaticTranslations()` их заполняет.
- `data-i18n="key"` → `textContent`;
- `data-i18n-html="key"` → `innerHTML` (только для строк из наших словарей, где есть `<b>` и т. п.);
- `data-i18n-placeholder`, `data-i18n-title`, `data-i18n-aria-label` → соответствующий атрибут.
- Русский текст **остаётся в HTML** как запасной вариант: до запуска JS страница всё равно будет на русском, как сейчас.
- `<title>` и `<meta name="description">` (если есть) тоже переводятся.
- Элементы, у которых текст меняет JS (например `aria-label` кнопки темы «Включить светлую тему»), переводятся в JS через `t()`, атрибут `data-i18n` на них не ставим, иначе два механизма будут перезаписывать друг друга.
- `<option>`: переводим только текст, `value` не трогаем (`all`, `week`, `month`, `year`).

### 2.4. Даты, числа, деньги

**Где:** все места с `'ru-RU'` в `app.js`. Сейчас это строки 51, 113, 357, 462, 486, 521, 549, 1000, 1320, 1855, 2253, 2328, 2690. Перед работой пересчитать: `grep -n "ru-RU" frontend/static/js/app.js`.

**Как:**
- Везде заменить `'ru-RU'` на `locale()`.
- Деньги (`money`, строка 49): число форматируется по локали, **символ валюты остаётся после числа во всех языках** (`12 500 ₸`, `12,500 ₸`), чтобы не менять вёрстку.
- Строка «с нами с …» (486), «Обновлено … в …» (2690) — собирать через `t()` с параметрами, а не склейкой строк: порядок слов в казахском другой («2026 жылғы 5 қарашадан бері біздемен»).
- **Проверить `kk-KZ` в Intl**: Chrome, Firefox и Safari должны давать казахские названия месяцев (`қараша`, `желтоқсан`). ### 2.5. Категории

**Зачем:** правило 0.4. Стандартные категории показываются на языке интерфейса, а в данных остаются русскими.

**Как:**
- Новая функция `categoryName(c)`: `c === UNCATEGORIZED` → `t('cat.uncategorized')`; `c.default_key` → `t('cat.' + c.default_key)`; иначе `c.name`. То же для описания: `categoryDescription(c)` → `t('cat.' + key + '.desc')` или `c.description`.
- **Заменить отображение `c.name` на `categoryName(c)` везде**: `categoryLabel` (строка 136), `categoryOptions`, фильтры, легенды графиков, бюджеты, окно чека, перенос позиций, рекомендации. Логика (`catKey`, `categoryByKey`, поиск по имени у гостя) **продолжает работать с `c.name`**.
- **Гость** (категории без `id` из `/api/categories/defaults`): у них тоже будет `key` (п. 3.2). Позиции гостя, как и раньше, хранят **русское** `name` категории, потому что при входе сервер ищет категорию по имени (`resolve_category_id`). Перевод только при показе. Это самое опасное место, тестировщик проверяет его отдельно (п. 5.3, сценарий G).
- **Редактирование стандартной категории:** в форме показывается переведённое название. В `PUT /api/categories/{id}` отправлять **только поля, которые пользователь реально изменил**. Если пользователь открыл и закрыл форму или изменил только иконку, `name`/`description` не отправляются, и категория остаётся стандартной с `default_key`. Если изменил название, отправляется новое название, бэк сбрасывает `default_key` (п. 3.2), и дальше категория показывается как пользовательская.
- Поиск по категориям в фильтрах ищет и по переведённому, и по исходному названию.

2. **Русские тексты копируются из текущего кода буква в букву**, чтобы старые тесты проходили (правило 0.1).
3. Новое исключение `AppError(status_code, code, **params)` и обработчик, который отвечает `{"detail": tr(code, lang, **params), "code": code}`. Поле `detail` остаётся **строкой**, как сейчас, а `code` добавляется. Все `HTTPException(detail="…")` в `server.py` перевести на `AppError`. Список мест: `grep -n "detail=" server.py`. 5. **Ошибки валидации 422** (обработчик в `server.py`, строка 156):
   - В своих валидаторах (`app/schemas.py`: `ItemIn`, `Preferences*`, даты, валюты) вместо `raise ValueError("текст")` использовать `PydanticCustomError("код", "русский текст", {параметры})`. Тогда в `exc.errors()` будет `type = "код"` и `ctx` с параметрами.

Встроенные ошибки Pydantic (`missing`, `int_parsing`, `float_parsing`, `string_too_long`, …) переводятся общими сообщениями из `MESSAGES` (`"missing": "Обязательное поле"` / `"Міндетті өріс"` / `"Required field"`). Неизвестный `type` → прежнее поведение, текст Pydantic.

### 4.1. Рекомендации на трёх языках (`advisor.py`)

**Зачем:** главная ML-задача недели. Рекомендации — самый «текстовый» раздел сайта.

**Как:**
1. Сигнатура: `generate_insights(snapshot, provider="gemini", language="ru")`. Если `language` не передан, берётся `snapshot.get("language", "ru")`. Неизвестный → `ru`. **Без `language` всё работает и пишет по-русски, как сейчас.**
2. **Промпт** (`_build_prompt`, строка 418): инструкции остаются на русском (их проверяли), в конце добавить жёсткое требование языка ответа:
   - `kk`: «Пиши `title`, `text` и `summary` ТОЛЬКО на казахском языке (кириллица, с буквами ә, ғ, қ, ң, ө, ұ, ү, һ, і). Названия категорий бери из поля display_name.»
   - `en`: «Write `title`, `text` and `summary` ONLY in English. Use category names from display_name.»
   - В `clean_snap` передавать `display_name` категории (от бэка, п. 3.5.2). Если его нет, `name`.
3. **Поля, которые НЕ переводятся и не зависят от языка:** `id` (`"over_budget:4:2026-11"`), `type`, `priority`, `category_id`, `action.kind`. Иначе на фронте сломается скрытие карточек (п. 2.8).
4. **Проверка чисел** (`_extract_numbers_from_text`, строка 302; `_has_hallucinated_numbers`, строка 316) должна понимать форматы всех языков:
   - ru/kk: `12 500`, `12 500,50`, `12 500 ₸`, `35%`;
   - en: `12,500`, `12,500.50`, `₸12,500`, `35%`.
   Без этого **каждый английский ответ будет отбракован** как «выдуманные числа», и пользователь всегда будет видеть шаблоны. Обязательно покрыть тестами.
5. **Проверка языка ответа:** новая функция `_looks_like_language(text, lang)`:
   - `en` — в буквах ≥ 80% латиницы;
   - `kk` — кириллица, и в тексте ≥ 50 букв есть хотя бы одна из `әғқңөұүһі`;
   - `ru` — как сейчас, без проверки.
   Если `summary` или больше половины карточек не прошли проверку, ответ считается невалидным, и используется `build_rule_insights` на нужном языке. Пороги подобрать на оценке (п. 4.4) и сообщить бэку (п. 3.5.8).
6. **Шаблонные советы** (`build_rule_insights`, строка 189): все тексты карточек и `summary` на трёх языках. Сделать словарь шаблонов `RULE_TEMPLATES[lang][type]` со `str.format` и параметрами. Русские шаблоны скопировать **буква в букву** (тесты `ml/tests/test_advisor.py` должны пройти без правок). Казахский текст — на проверку носителю (п. 5.6).
7. **Деньги** (`_format_money`, строка 180): `language` в параметрах. `ru`/`kk` — как сейчас (`12 500 ₸`, `12 500,50 ₸`), `en` — `12,500 ₸`, `12,500.50 ₸`. Символ после числа, как на фронте (п. 2.4).
8. **Ollama:** маленькие локальные модели плохо пишут по-казахски. Если `provider == "ollama"` и `language == "kk"`, проверка из п. 5 почти всегда будет отправлять к шаблонам. Это нормально, но записать в `results.md`, чтобы никто не думал, что это баг.

### 4.2. Категоризация товаров на казахском и английском (`categorize.py`)

**Зачем:** пользователи с казахским и английским интерфейсом будут вводить товары вручную на своём языке («сүт», «нан», «milk», «bread»), а ещё создавать категории с названиями и описаниями на своём языке.

**Как:**

### 4.3. Исправление алфавитов с казахскими буквами (`textfix.py`)

**Зачем:** `_CYR` и `_WORD` (`ml/app/textfix.py`, строки 26–29) не знают букв `әғқңөұүһі`. Казахское слово из чека или ручного ввода («Сүт 2,5%», «Қант») режется на куски, и куски могут «исправиться» в латиницу.

**Как:**
- Добавить казахские буквы в `_CYR` и `_WORD`. В таблицы замен `_TO_LAT`/`_TO_CYR` их **не** добавлять: у них нет латинских двойников. Исключение — `і`, она уже есть (`і` ↔ `i`). Проверить, что казахское слово с `і` («Тіс пастасы») не превращается в латиницу.
- Слово, где есть хотя бы одна казахская буква, считается кириллическим и в латиницу не переводится.
- Тесты в `ml/tests/test_textfix_and_keywords.py`: «Сүт», «Қант», «Тіс пастасы», «Ұн 2кг», «Lепог» (старый случай, должен работать как раньше).

## 6. Контракты API (изменения)

Всё ниже — **добавления**. Существующие поля и коды ответов не меняются.

**Все запросы:** необязательный заголовок `Accept-Language: ru | kk | en` (`kz` = `kk`; `kk-KZ`, `en-US` тоже принимаются). Без него — `ru`.

**Ошибки:**
```json
{ "detail": "Чек табылмады", "code": "receipt_not_found" }
```
`detail` — строка на языке запроса (как раньше), `code` — новое поле, стабильный машинный код. Для 422 `detail` по-прежнему список, `msg` внутри на языке запроса.

**`UserOut.preferences`:**
```json
{ "theme": "system", "accent": "violet", "ai_insights": false, "language": "ru" }
```
`PATCH /api/auth/me` `{"preferences": {"language": "kk"}}` — меняет только язык.

**`CategoryOut`** и **`/api/categories/defaults`:** новое поле `default_key` (`"groceries"` … `"other"` или `null`). `name` и `description` — как в базе (русские у стандартных).

**`GET /api/currencies`:** `name` на языке запроса. Формат прежний.

**`GET/POST /api/insights`:** язык рекомендаций = язык запроса. `GET` отдаёт последний анализ на этом языке или `{"insights": null}`. Лимит повторной генерации — отдельно по каждому языку. Поля `id`, `type`, `category_id`, `action` от языка не зависят.

**ML, `generate_insights(snapshot, provider, language="ru")`:** в `snapshot` есть `language` и `categories[].display_name`.

**Зависимости:**
- Фронт может работать с понедельника **без бэка**: переводы стандартных категорий делаются по русскому названию, пока не пришёл `default_key`. Временная таблица «русское имя → ключ» в `i18n.js` удаляется, когда бэк выложит 3.2.
- Переключатель сохраняет язык на сервере только после 3.1 (понедельник). До этого только `localStorage`.

- Казахский словарь терминов (1.4) и категории (1.3) нужны всем, поэтому носитель проверяет их **первыми**, в понедельник. Если он меняет перевод, правка сначала в этом файле, потом в коде.
